# 08 · 기록을 블로그와 포트폴리오로 바꾸기

## 목표·준비·산출물

- 목표: 자신이 맡은 문제·판단·실행·검증을 근거와 함께 설명한다.

- 산출물: 짧은 블로그 초안, 프로젝트 소개 한 장, 주장과 증거의 대응표.
- 완료 기준: 공개 발행 없이도 읽고 검토할 수 있는 로컬 초안. 본인 기여와 AI 도움을 구분한다.

## 개념 설명

블로그는 독자가 문제 해결 과정을 따라가도록 쓴다. 프로젝트 소개는 평가자가 문제·역할·핵심 판단·결과를 빠르게 확인하도록 쓴다. 같은 원자료를 쓰지만 강조점이 다르다. 블로그에는 처음 예상과 실제 관찰이 갈린 지점을 넣고, 소개에는 그 상황에서 자신이 내린 결정과 확인 근거를 앞에 둔다.

“Git을 사용했다”는 도구 목록이다. “같은 문장의 입력·출력 단위 수정이 충돌했을 때 CSV 헤더를 확인해 둘을 보존하는 문장으로 병합했다”는 판단과 행동이다. 후자는 코드가 적은 교육용 사례라도 구체적으로 평가할 수 있다. 규모를 키워 보이려고 연구실 운영 개선, 팀 전체 생산성 향상, 처리 시간 단축을 만들어 넣지 않는다.

증거는 주장에 맞춰 고른다. 파일이 있다는 주장은 파일 경로로, 변경했다는 주장은 diff·커밋으로, 값이 맞다는 주장은 입력·계산·검증 결과로 뒷받침한다. “팀원이 재현했다”는 주장은 실제 다른 사람의 확인 기록이 필요하다. 화면 캡처 하나가 모든 주장을 대신하지 못한다.

한계를 적을 때도 추상적인 “부족하지만 열심히 했다”로 끝내지 않는다. 합성 입력만 사용했는지, 오류 데이터 검사는 구현했는지, GitHub PR은 수행했는지, 비교 실험이 있는지 적는다. 다음 행동은 그 한계를 확인할 작은 작업으로 제시한다.

## 강사 진행 장면

### 장면 1 · 도구 이름을 사건으로 바꾸기

**강사 발화:** “‘AI와 GitHub를 활용한 데이터 프로젝트’만 들으면 여러분이 무엇을 판단했는지 알 수 없습니다. 가장 설명할 수 있는 사건 하나를 고릅시다.”

**판서:** `문제 → 내 판단 → 실행 → 증거 → 한계`를 쓴다.

**예상 학생 답:** “입력과 출력 단위 설명이 충돌했을 때 둘을 구분해 병합한 사건을 설명하겠습니다.”

### 장면 2 · 과장 문장 줄이기

**강사 발화:** “‘분석 효율을 80% 개선했다’는 문장을 쓰고 싶습니다. 전후 시간과 같은 조건의 측정이 있나요?”

**화면:** 현재 증거인 README·CSV·Git log만 보여준다.

**예상 학생 답:** “시간 측정이 없으므로 그 수치를 쓸 수 없습니다. 확인한 것은 상태 구분과 단위 설명 통합입니다.”

### 장면 3 · AI 도움과 내 판단 나누기

**강사 발화:** “AI가 충돌 해결 문장을 제안했습니다. 내가 직접 한 일은 무엇인가요? 제안받은 문장을 검증했다면 그 방법을 설명하세요.”

**판서:** `AI: 후보 문장 / 학생: CSV 단위 확인·diff 검토·실행 관찰`을 쓰되 실제 수행한 경우에만 해당된다고 표시한다.

**예상 학생 답:** “AI가 문장 후보를 만들었고, 저는 voltage_mv 헤더와 평균 계산을 대조했습니다.”

### 장면 4 · 질문에 파일로 답하기

**강사 발화:** “면담자가 ‘어떻게 확인했나요?’라고 묻습니다. ‘AI에게 물었습니다’ 다음에 어떤 자료를 보여줄 수 있나요?”

**화면:** samples.csv, 계산식, 해당 커밋 diff, 미검증 항목을 순서대로 연다.

**예상 학생 답:** “세 전압값과 단위 변환식, 문서 변경 이력을 보여줍니다. 프로그램 실행은 안 했다고 설명합니다.”

## 함께 읽을 완성 예시 1 · 블로그 초안

다음은 **수업 시나리오를 설명하는 교육용 글**이다. 특정 학생의 실제 수행담이 아니다. 빈 양식이 아닌 완성 글의 구조를 읽고, 자신의 글은 실제 관찰로 다시 쓴다.

### Git은 평균이 맞는지 판단하지 않는다

합성 측정 CSV와 README만으로도 Git을 배울 수 있다. 이번 교육 사례의 입력은 1000, 2000, 3000mV다. V로 변환하면 1, 2, 3이고 평균은 2V다. 분석 프로그램은 없으며, 계산은 손계산으로 확인하는 범위다.

수업은 README의 `Mean: 2`를 일부러 `Mean: 2.5`로 바꾸고 커밋하는 상황을 만든다. Git은 이 변경을 기록할 수 있다. 이때 커밋이 성공했다는 사실은 숫자가 맞다는 근거가 아니다. Git은 어떤 상태를 남겼는지를 관리하고, 값의 타당성은 입력과 계산으로 확인해야 한다.

오류를 찾는 순서는 단순하다. 먼저 samples.csv의 세 값을 확인한다. 평균 계산식 `(1000 + 2000 + 3000) / 3 / 1000`은 2다. 이어 `git log --oneline -3`으로 최근 이력을 찾고 `git show HEAD -- README.md`로 방금 기록한 변경을 확인한다. 이 예제에서는 HEAD가 의도적으로 만든 오류 커밋일 때만 다음 단계로 간다.

복구에는 `git revert --no-edit HEAD`를 사용한다. 실행 뒤 확인할 것은 현재 값, 이력, 작업 상태다. README의 Mean은 2로 돌아와야 하고, 잘못된 커밋과 이를 상쇄하는 새 커밋은 모두 남아 있어야 한다. 수업에서 확인한 실제 해시와 출력은 각자의 기록에 붙인다.

이 사례가 보여주는 것은 버전 관리와 검증의 역할 차이다. 변경 이력이 있어야 무엇을 고쳤는지 찾기 쉽다. 동시에 올바른 예상값과 입력이 있어야 무엇이 잘못됐는지 판단할 수 있다. AI가 “수정 완료”라고 말하더라도 이 두 확인은 필요하다.

적용 범위도 작게 잡아야 한다. 이 사례는 방금 만든 일반 커밋 하나를 바로 상쇄한다. 오래된 커밋이나 여러 수정이 얽힌 상황을 모두 해결했다고 주장할 수 없다. 실제 연구 데이터를 처리하거나 자동 분석 시스템을 배포한 사례도 아니다. 다음 연습은 단위 설명이 갈라진 두 브랜치를 비교하고, 입력 mV와 출력 V가 모두 드러나는 문장으로 병합하는 것이다.

## 함께 읽을 완성 예시 2 · 프로젝트 소개 한 장

아래 소개 역시 **수업용 사례 소개**다. 개인의 실무 성과·팀 기여를 꾸며 넣지 않았다. 학생 제출본에서는 실제 맡은 역할과 확인한 증거로 바꾼다.

### 합성 측정 자료로 배우는 Git 검증·기록 실습

**목적:** 같은 문서의 수정 이력을 읽고 잘못된 변경을 상쇄하며, 입력·출력 단위 설명을 검증 가능한 형태로 남기는 교육 과제다.

**자료와 범위:** samples.csv의 세 전압값과 README를 사용한다. scratch.txt는 복구 연습에만 쓰며 .gitignore는 임시 출력 등을 제외한다. 자동 분석 프로그램, 실제 장비 데이터, 성능 측정은 포함하지 않는다.

**핵심 문제:** 단위 설명을 고치는 두 브랜치가 같은 줄을 다르게 수정한다. main은 `Unit: input mV`, docs/units는 `Unit: output V`를 기록한다. 한쪽만 선택하면 다른 쪽 설명을 잃는다.

**판단과 처리:** CSV의 voltage_mv와 V 기준 평균을 대조한다. 최종 문장은 `Unit: input mV, output V`로 정한다. 충돌 표시 제거 뒤 staged diff를 읽고 Mean·Status·Source가 보존됐는지 확인하는 절차를 사용한다.

**제출할 증거:** 실제 수행한 저장소의 두 분기 커밋과 병합 커밋, 최종 README, 합성 CSV, 평균 2V의 손계산, status와 내용 확인 기록이다. 이 소개 자체는 그 수행 증거를 대신하지 않는다.

**역할 설명:** 강의는 충돌 상황과 완료 기준을 제공한다. 학습자는 자신이 직접 한 상태 예측·단위 판단·명령 실행·검증을 설명한다. AI 도움을 받았다면 제안·문서 작성·해석 중 어느 부분인지 밝힌다. 수행하지 않은 항목은 본인 역할로 쓰지 않는다.

**확인 가능한 성과의 범위:** 실제 수행 기록이 갖춰지면 브랜치의 분기·병합과 충돌 해결 이유를 설명할 수 있다는 근거가 된다. 연구실 생산성 향상, 서비스 운영, 자동 분석 정확성, GitHub 협업 성공을 입증하는 자료는 아니다.

**다음 단계:** 구현된 CSV 분석 프로그램이 생기면 정상·오류 입력으로 실행하고, 실제 명령과 결과를 README에 추가한다. 공동 작업이 필요해지면 권한을 확인한 원격 저장소에서 PR 검토를 진행한다.

## 학생 활동 · 자신의 글로 바꾸기

1. 실제 작업 기록에서 사건 하나를 고른다. 교육용 오류였다면 본문 첫 부분에 그 사실을 쓴다.
2. 독자를 정한다. 블로그는 같은 문제를 배울 후배, 소개는 역할과 근거를 확인할 사람으로 잡아도 된다.
3. 블로그에는 문제·첫 예상·관찰·확인·변경·한계를 문단으로 쓴다. 예상 기록이 없으면 당시 생각을 사후에 만들어 넣지 않는다.
4. 소개에는 목적·내 역할·핵심 판단·결과 근거·한계를 한 장에 담는다.
5. 주장마다 파일·커밋·계산·실행 기록 중 근거를 연결한다. 근거가 없으면 주장 범위를 줄이거나 미확인으로 바꾼다.
6. 짝에게 “무엇을 직접 했나, 무엇으로 확인했나, 무엇을 하지 않았나”를 설명하게 한다. 실제 답을 기록하고 오해된 문장을 고친다.

**풀이·판정 예:** “충돌을 해결했다”에는 병합 커밋과 최종 문장, “평균을 확인했다”에는 CSV와 계산식, “다른 사람이 실행했다”에는 실제 재현 기록이 필요하다. 코드 없는 실습을 프로그램 개발 성과로 표현하면 수정한다. 공개 발행·사이트 제작·조회 수는 통과 조건이 아니다.

## 질문·마무리·출처

- **작은 실습도 소개할 가치가 있나요?** 교육용 범위와 본인 판단을 명확히 쓰면 학습 경험을 설명할 수 있다. 실무 성과인 것처럼 포장하지 않는다.
- **실패는 빼도 되나요?** 최종 판단을 이해하는 데 필요한 실패와 교정은 남긴다. 모든 시행착오를 나열할 필요는 없다.
- **AI로 문장을 다듬어도 되나요?** 가능하다. 숫자·역할·검증을 원자료와 대조하고 없는 사실을 추가하지 않는다.

통과 기준은 두 글의 완성, 주장별 증거, 본인·AI 역할 구분, 한계 명시다. 다음 시작점은 새 기능을 실제 구현·검증했을 때 [README와 작업 기록](07-records.md)을 갱신하고 해당 경험을 글에 반영하는 일이다.
