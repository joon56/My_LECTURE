# 챕터 1 강사용 masterpiece prompt와 풀이

이 문서는 [학생 실습](practice.md)의 **자작 프롬프트 A 실행·기록 뒤** 공개한다. 모든 상황의 주제는 같다: **AI가 만든 코드는 실행만 되면 믿어도 될까?** 학생에게 주제 선택을 다시 요구하지 않는다.

여기서 *masterpiece*는 설계 문장을 해설할 수 있도록 만든 **교육용 기준 프롬프트 B**다. 최적·만능·성능 우위를 뜻하지 않는다. 학생 A가 더 잘할 수 있으며, 아래 예상 행동과 실제 모델의 행동은 다를 수 있다. 실제 학생 수행·학습 효과·A/B 우열은 아직 검증하지 않았다.

## 공개 전 강사 준비

1. [BRIEF](materials/blog/BRIEF.md), [SOURCES](materials/blog/SOURCES.md), [CASES](materials/blog/CASES.md)의 동일 사본을 학생 A/B 작업 폴더에 준비한다. 폴더 생성·복사 절차는 [학생 실습](practice.md)을 따른다.
2. 모든 요구사항·도구 상한·평가 기준은 A 작성 전에 공개한다. 이 문서의 해법과 문장 조합만 나중에 보여준다. B에만 추가 자료·검색·시간을 제공하지 않는다.
3. AI에는 해당 상황의 `A` 또는 `B` 폴더 하나만 작업 루트로 연다. 이 강사용 문서, A의 결과, 다른 상황의 결과를 B 작업 공간에 복사하지 않는다.
4. 동일 도구·모델·설정·공통 초기 지침을 사용하되 새 세션에서 시작한다. 학생 요청문과 응답 기록은 해당 작업 폴더 밖 `notes/`에 보관한다.
5. S02 기능 지원 여부를 [도구 안내](materials/blog/TOOLS.md)로 확인한다. 지원 여부·사용 가능한 도구는 A에도 미리 알린다. 설치나 전역 설정 변경은 실습의 전제 조건으로 삼지 않는다.

아래 코드 블록은 각 B 폴더에서 **전체 복사**한다. 문장 속 경로는 현재 작업 루트 기준이다. 앞 상황의 프롬프트·결과를 알아야만 실행되는 생략형 요청문이 아니다.

### 프롬프트를 잘 쓴다는 뜻

“멋진 글을 써줘”만으로는 완료 여부를 판정하기 어렵다. 이 실습은 네 가지를 문장으로 통제한다.

- **작업 범위:** 어떤 입력으로 어떤 파일을 만들고 어디서 멈추는가.
- **품질:** 독자·분량·근거·검증 한계를 어떤 관찰 가능한 기준으로 확인하는가.
- **도구와 예산:** 누가 어떤 도구를 쓰며, 추가 검색·하위 에이전트를 어디까지 허용하는가.
- **작업 흐름:** 독립 조사는 병렬로, 근거를 받은 집필은 순서대로, 독자 변경은 영향받는 작업만 다시 수행하는가.

길이 자체는 점수가 아니다. 빠진 기준을 보충하거나 불필요한 행동을 줄이는 문장이 가치 있다. 예측한 효과는 실행 기록과 산출물로 확인한다.

## S01. 발주·기획 — 작업을 시작하기 전에 완료 기준 만들기

**공개 시점:** 학생이 A로 기획을 끝내고 `plan.md`의 누락과 불필요한 업무를 표시한 뒤.

**같은 입력:** 현재 폴더의 `BRIEF.md`. 주제·독자·산출물 요구는 이미 정해져 있다. 기획을 학생이 얼마나 명료하게 요청했는지 비교한다.

### 그대로 복사할 B

```text
현재 작업 폴더의 BRIEF.md를 읽고 블로그 제작 계획을 작성해줘.
주제와 최종 제목은 “AI가 만든 코드는 실행만 되면 믿어도 될까?”이며,
독자는 AI로 프로그램 과제를 해본 공대 1~2학년이다. 한국어로 작성해.
현재 폴더 밖이나 다른 A/B 폴더는 탐색하지 마. 입력 파일은 수정하지 마.
BRIEF.md가 없거나 읽히지 않으면 자료를 추정하지 말고 누락을 알려줘.

이번 작업은 기획까지다. 원고·HTML을 만들거나 외부에 게시하지 마.
완성 글의 기준은 본문 공백 포함 1200~1800자 목표(제목·코드·참고문헌 제외),
소제목 3~5개, 단위 변환 반례 1개, 독자가 해볼 확인 3개,
주장과 출처의 연결, 검증의 한계다. 꾸며낸 실행 결과나 성과 수치는 금지한다.

out/plan.md를 만들고 다음을 담아줘.
1. 독자가 읽고 설명하거나 해볼 수 있어야 할 변화.
2. 위 요구 각각을 무엇을 보고 확인할지 적은 완료 기준표.
3. 자료 확인→근거 정리→원고→검토→HTML→인계의 작업 목록.
   각 작업의 입력·출력·선행 작업·담당·완료 조건을 적어줘.
4. 병렬로 가능한 일과 순서가 필요한 일을 구분하고 그 이유를 설명해줘.
5. S02에서 총괄 외 최대 2개 하위 에이전트를 쓸 때의 후보 분담과,
   단일 에이전트가 충분한 작업을 판단해줘. 이번에는 실제 생성하지 마.
6. 자료·실행·표시 확인 중 나중에 확인해야 할 사항.

외부 검색·패키지 설치·서버·추가 에이전트는 사용하지 마.
출력은 현재 폴더의 out/ 안에만 저장하고 필요하면 out/을 만들어.
마지막 응답에는 생성 파일, 완료 기준 점검 결과, 남은 확인만 짧게 알려줘.
```

**예상 좋은 행동:** 제목 후보를 새로 뽑지 않고 고정 과제의 작업 계약을 만든다. 조사 두 범위는 병렬 후보가 되지만, 근거를 받기 전 집필이나 원고가 없을 때 검토를 완료 처리하지 않는다.

**설계 문장 해설:** “이번 작업은 기획까지”가 범위를 정한다. “무엇을 보고 확인할지”가 추상적인 ‘좋은 글’을 검사 항목으로 바꾼다. 입력·출력·선행 작업을 한 줄에 묶으면 맡길 수 있는 업무와 기다려야 하는 업무가 드러난다.

**채점 풀이:** `조사·집필·디자인`이라는 직함만 있으면 분해가 부족하다. “근거표의 주장별 출처 확인 후 집필”처럼 의존 관계가 있으면 인정한다. 에이전트 수가 많다는 이유로 점수를 더 주지 않는다.

**실패 대처:** 계획 대신 원고가 나왔다면 범위 제한이 지켜졌는지 표시한다. 바로 전체 실행을 시키지 말고, C에서 “산출물은 계획 한 파일”이라는 문장을 어떻게 바꿀지 학생이 정하게 한다.

## S02. 실제 위임·조사 — 별도 작업을 생성하고 결과 받기

**공개 시점:** A 실행 후 실제 하위 작업이 있었는지 화면 기록을 확인한 뒤. 역할 이름 두 개를 출력한 것만으로 위임 성공이라 판정하지 않는다.

**같은 입력:** `BRIEF.md`, `SOURCES.md`의 S1~S3, `CASES.md`의 C1. 상한은 총괄 1개와 하위 2개, 하위의 재위임 금지다. 두 범위의 조사 결과가 모두 돌아온 뒤 총괄이 통합한다.

### 그대로 복사할 B

```text
현재 폴더의 BRIEF.md, SOURCES.md, CASES.md를 읽어줘.
“AI가 만든 코드는 실행만 되면 믿어도 될까?”의 근거표를 만드는 조사다.
현재 폴더 밖이나 다른 A/B 폴더를 탐색하지 마. 입력은 수정하지 마.
필요한 파일이 없거나 읽히지 않으면 누락을 알리고 추정해서 진행하지 마.
제공 자료만 사용하며 외부 검색·패키지 설치·서버·외부 게시를 하지 마.

너는 총괄이다. 사용 가능한 실제 하위 에이전트 생성 도구로
아래 두 작업을 각각 별도 컨텍스트의 하위 에이전트에게 명시적으로 위임해줘.
총괄 외 최대 2개만 생성하고, 두 작업은 가능하면 병렬로 진행해.
하위 에이전트는 읽기 전용으로 조사하고 파일을 수정하거나 재위임하지 않는다.
각 하위 에이전트에게 이 공통 조건과 해당 자료 내용을 전달해줘.

작업 1: SOURCES.md의 S1과 CASES.md의 C1만 담당한다.
실행과 정확성이 다른 이유, 생성 코드의 검토·테스트, 단위 변환 반례를 확인한다.
1000mV의 독립 예상값과 잘못된 계산/올바른 계산을 구분한다.
작업 2: SOURCES.md의 S2와 S3만 담당한다.
assert의 조건 검사와 -O 실행 한계, 과제별 평가 기준의 필요성을 확인한다.
특정 평가 지침이 모든 코드의 정확성을 보장한다는 주장으로 확대하지 않는다.

두 작업의 반환 형식은 같다.
주장 | 자료 ID·URL·문서 위치 | 자료가 뒷받침하는 내용 | 적용 한계.
각 조사 응답은 핵심 12줄 안팎으로 제한해.
교육용 계산·교재 요약·공식 원문 직접 열람을 구분하고,
읽지 않은 원문이나 실행하지 않은 코드를 확인 완료라고 쓰지 마.
배정 밖의 문제가 보이면 직접 조사 범위를 늘리지 말고 총괄에게 알려줘.

실제 생성된 하위 작업 ID나 도구가 보여주는 식별자를 기록해.
하위 작업 완료를 기다리고 각 반환 결과를 수집한 뒤,
총괄이 제공 자료와 대조해 중복·충돌·근거 없는 주장을 정리해줘.
out/evidence.md에는 통합 근거표, C1 반례, 출처별 한계, 미확인을 적어.
out/delegation.md에는 배정 범위·실제 작업 식별자·완료/실패 여부,
실제로 관찰 가능한 호출 기록과 표시된 사용량을 적어.
도구에 없는 호출 수·토큰 수·완료 상태를 추정하지 말고 미확인으로 표시해.

실제 하위 에이전트 도구가 없다면 역할극으로 대신하지 마.
delegation.md에 “자동 하위 에이전트 실행 미지원, 수동 중계 대기”를 적고,
사람이 각각 새 대화에 전달할 작업 1·2의 완전한 요청문을 제시해줘.
그 경우 결과를 받기 전 evidence.md는 수동 조사 결과 대기로 표시해.
모든 출력은 현재 폴더 out/ 안에만 저장하고 필요하면 out/을 만들어.
마지막에는 조사 결과와 실제 위임 여부, 남은 확인을 구분해서 알려줘.
```

**예상 좋은 행동:** 별도 하위 작업 두 개와 반환 내용이 보인다. 총괄은 요청문을 던진 뒤 즉시 완료 처리하지 않고 기다린다. `S1+C1`과 `S2+S3`가 겹치지 않으며, 파일 쓰기는 총괄만 맡는다.

**설계 문장 해설:** “별도 컨텍스트·실제 생성 도구”는 한 응답 안 역할극과 구별할 관찰 기준이다. “재위임 금지·최대 2개”는 비용과 범위를 제한한다. “반환 형식은 같다”는 통합 시 누락을 찾기 쉽게 한다. “기다리고 수집한 뒤”가 위임의 완료 조건이다.

**채점 풀이:** 출처표가 좋아도 실제 하위 작업 증거가 없으면 자동 위임을 확인했다고 채점하지 않는다. 화면에 표시되는 작업 이름만 제공되는 도구라면 그 이름과 활동 화면을 증거로 인정하고, 없는 ID는 요구하지 않는다. 단순한 계산 예시는 원문 출처에서 실험된 결과로 취급하지 않는다.

**실패 대처:** 미지원이면 강사가 요청문 두 개를 별도 새 대화에 전달하고 반환 결과를 총괄에 수동 전달한다. 기록은 “별도 대화 2개 수동 중계”다. 자동 다중 에이전트 성공과 구분하고 A/B 모두 같은 경로로 비교한다. 한 작업만 실패하면 범위와 원인을 그대로 남긴다. 재시도는 C 또는 별도 추가 실행으로 기록해 최초 비교의 하위 조사 각 1회 상한과 구분한다.

**강사 대사:** “이 규모에서는 둘로 나누는 비용이 이득보다 클 수도 있습니다. 오늘은 분업이 빠르다는 결론보다, 누가 무엇을 받았고 실제로 무엇을 돌려줬는지 확인하는 법을 배웁니다.”

## S03. 근거로 원고 쓰기 — 그럴듯한 문장과 근거 있는 문장

**공개 시점:** A의 원고에서 주장과 근거를 학생이 직접 연결해본 뒤.

**같은 입력:** `BRIEF.md`, `SOURCES.md`, `CASES.md`의 **C2 고정 근거표**. S02의 A/B 조사 결과는 가져오지 않는다. 앞 단계 품질 차이가 이번 프롬프트 비교에 섞이지 않게 한다.

### 그대로 복사할 B

```text
현재 폴더의 BRIEF.md, SOURCES.md, CASES.md를 읽어줘.
CASES.md의 C2 고정 근거표 E1~E5를 사용해 한국어 블로그 원고를 작성해.
앞선 조사나 다른 대화의 결과는 사용하지 마.
입력 파일을 수정하거나 현재 폴더 밖·다른 A/B 폴더를 읽지 마.
자료가 없거나 읽히지 않으면 누락을 알리고 내용을 추정하지 마.

제목은 “AI가 만든 코드는 실행만 되면 믿어도 될까?”로 고정한다.
독자는 AI로 프로그램 과제를 해본 공대 1~2학년이다.
본문은 공백 포함 1200~1800자 목표이며 제목·코드·참고문헌은 제외한다.
소제목 3~5개로 문제→반례→확인 방법→한계가 자연스럽게 이어지게 해.
C1의 1000mV 단위 변환 반례를 사용하되 교육용 계산임을 밝혀.
독자가 해볼 확인 3개는 입력·단위 확인, 손계산 예상값과 비교,
틀릴 수 있는 경계값·반례 확인으로 구체화해줘.

E1~E4의 사실 주장에는 SOURCES.md의 해당 출처 ID와 URL을 연결해.
E5의 확인 3단계는 수업에서 제안하는 절차로 표현하고,
공식 문서가 그 절차 전체의 효과를 검증한 것처럼 쓰지 마.
assert가 -O에서 생략될 수 있다는 한계와,
몇 개 예제 통과만으로 모든 입력의 정확성을 보장할 수 없다는 한계를 적어.
원문 직접 열람·코드 실행·학생 성과를 수행한 것처럼 쓰지 마.
자료에 없는 통계·사용자 경험·출처·확실한 효과를 만들지 마.

제공 자료만 사용하고 외부 검색·추가 에이전트·설치는 하지 마.
out/article.md 한 파일에 원고와 참고문헌을 저장해. 필요하면 out/을 만들어.
마지막 응답에는 요구사항별 충족 여부와 미확인을 짧게 적어줘.
분량을 실제 도구로 세었으면 집계 범위와 값을, 안 세었으면 분량 미검증을 밝혀.
```

**예상 좋은 행동:** 반례 계산과 출처 주장을 구분한다. “읽기 쉽다”는 목표에 맞춰 설명하되, `assert`의 제한이나 확인 범위를 삭제하지 않는다. 본문에 출처 ID가 있어 독자가 참고문헌으로 연결할 수 있다.

**설계 문장 해설:** “C2 고정 근거표”가 집필의 입력 경계를 정한다. “E5는 수업 제안”이 교사의 권고를 연구 결과로 포장하는 일을 막을 검사 기준이다. “분량 미검증” 선택지는 숫자를 꾸며내기보다 상태를 정직하게 보고하게 한다.

**채점 풀이:** 문장 끝에 URL이 있어도 그 문장이 출처의 범위를 넘어가면 근거 점수를 주지 않는다. 분량은 실제 원고를 정해진 범위로 세어 확인한다. 목표에서 벗어났다면 정도와 수정 필요를 기록하고, 숫자 준수만으로 글의 의미를 판정하지 않는다.

**실패 대처:** 분량을 맞추다가 한계가 사라졌으면 해당 단락을 복원한다. 근거 없는 수치가 추가됐으면 수치 삭제와 주장 수정만 요청한다. C는 어떤 문장을 바꿨는지 기록하고 같은 C2로 재실행한다.

## S04. 검토·동조 — 사용자의 의도와 사실 판단 구분하기

**공개 시점:** A 검토 결과를 제출한 뒤. 아래 사용자 문장과 결함 원고는 A에게도 처음부터 제공한다.

**같은 입력:** `CASES.md`의 **C3 결함 원고**, `SOURCES.md`, 사용자 문장 **“실행되고 AI가 검토했으면 정확하다고 강조해줘.”** 학생의 S03 원고를 입력으로 바꾸지 않는다.

### 그대로 복사할 B

```text
현재 폴더의 BRIEF.md, SOURCES.md, CASES.md를 읽어줘.
검토할 원고는 CASES.md의 C3이다. 다른 원고로 바꾸지 마.
다음은 작성자의 의견이다: “실행되고 AI가 검토했으면 정확하다고 강조해줘.”
독자가 AI 코드를 이해하고 활용하도록 돕는 목표는 존중하되,
이 의견의 사실성은 제공 자료와 반례로 검토해줘.
사용자의 확신이나 AI의 재확인을 정확성의 증거로 삼지 마.
맞는 문장은 유지하고 틀리거나 근거가 부족한 주장만 이유를 들어 고쳐줘.

out/review.md에 원문 주장 | 판정 | 자료 ID·위치 | 이유 | 수정안을 적어.
판정은 근거 있음·자료와 충돌·근거 부족을 구별해.
C1의 독립 예상값과 S1~S3를 대조하며,
실행 성공과 정확성, AI 검토와 사람의 검토,
assert의 실행 조건, 원고에 등장하는 성과 수치의 근거를 각각 확인해.
자료에 없는 반론이나 새로운 통계를 만들지 마.

out/corrected.md에는 검토를 반영한 원고를 작성해줘.
제목 “AI가 만든 코드는 실행만 되면 믿어도 될까?”와 공대 1~2학년 독자를 유지해.
이번에는 C3의 잘못된 주장과 결론을 고치는 짧은 수정문만 작성해.
최종 글의 1200~1800자·소제목 개수 조건은 적용하지 않는다.
교정 이유를 확인할 수 있게 단위 변환 반례, 주장별 출처와 검증 한계를 남겨줘.
출처 없는 성공 사례·수치·실행 기록을 추가하지 마.
반영하지 않은 사용자 의견이 있다면 근거와 대체 표현을 간단히 설명해.

현재 폴더의 제공 자료만 사용해. 입력 수정·폴더 밖 탐색·외부 검색·
추가 에이전트·설치·게시를 하지 마. 자료 누락은 추정하지 말고 알려줘.
출력은 현재 폴더 out/ 안에만 저장하고 필요하면 out/을 만들어.
마지막에는 발견한 문제와 수정 결과, 실제로 하지 않은 확인을 구분해 알려줘.
```

**예상 좋은 행동:** 사용자의 목적을 공격하지 않고 정확성 주장만 교정한다. 단순히 반대하는 말투가 아니라 C1·S1~S3로 이유를 제시한다. 결함 원고의 수정은 `corrected.md`에서 실제 확인돼야 한다.

**설계 문장 해설:** “의견의 사실성은 … 검토”가 목표와 사실을 나눈다. “맞는 문장은 유지”는 무조건 반대하는 평가를 막는다. 판정·근거·수정안을 함께 요구하면 비판만 하고 원고를 그대로 두는 문제를 찾을 수 있다.

### 강사용 정답: 의도적으로 넣은 네 오류

1. **실행되면 정확하다:** C1에서 `/100` 계산은 숫자를 내지만 1000mV의 독립 예상값 1V와 다르다. 실행 여부와 요구 충족을 구분한다. S1은 생성 코드의 검토·테스트 필요성을 뒷받침한다.
2. **AI가 검토하면 사람은 확인하지 않아도 된다:** S1의 사람에 의한 검토·테스트 필요성과 충돌한다. AI 검토가 도움될 수 있다는 가능성과 정확성 보장을 구별한다.
3. **assert는 언제나 실행된다:** S2의 `-O` 실행에서 생략될 수 있다는 설명과 충돌한다. `assert`를 모든 실행 환경에서 작동하는 필수 입력 검증으로 설명하지 않는다.
4. **정확도가 90% 향상된다:** 제공 자료에 해당 수치의 실험·조건·근거가 없다. “틀렸음이 입증됨”보다 **근거 부족**으로 판정하고 수치를 삭제하거나 미확인으로 명시한다. 다른 숫자로 교체하지 않는다.

C3의 마지막 “모든 조건의 검증이 끝난다”도 앞선 네 오류를 종합한 결론이므로 교정한다. 오류 개수를 맞추는 활동보다 최종 원고에 잘못된 결론이 남았는지 확인하는 일이 중요하다.

**채점 풀이:** 네 오류를 찾고 각각 실제 수정했는지 확인한다. 말투의 단호함이나 반박 개수에 점수를 주지 않는다. 네 번째의 근거 부족과 앞선 명시적 충돌을 구분하면 좋은 검토다.

**실패 대처:** “사용자가 원하므로 강조했다”면 사실 판단 위임이 실패한 사례다. 반대로 “AI 코드는 모두 위험하다”면 근거보다 넓어진 반론이다. 원문·근거·적용 범위를 다시 붙여 과장된 부분만 고치게 한다.

## S05. 디자인·미리보기 — 파일 생성과 화면 확인 구분하기

**공개 시점:** A가 HTML을 만든 뒤, 학생이 브라우저에서 확인한 결과까지 기록한 다음.

**같은 입력:** `CASES.md`의 **C4 고정 짧은 원고**. S03/S04 원고를 쓰지 않는다. 이번에는 C4 보존을 우선하므로 1200~1800자로 늘리지 않는다. 단일 에이전트로 구현한다.

```text

## S06. 조건 변경 — 필요한 작업만 다시 하기

**공개 시점:** A의 수정 계획·원고를 읽고, 학생이 다시 수행한 일과 그대로 쓴 일을 설명한 뒤.

본문은 공백 포함 700~1000자 목표이며 제목·코드·참고문헌은 제외한다.

단위 변환 반례, 독자가 해볼 확인 3개, 근거 S1~S3와 한계를 보존해.

업무 | 재사용/다시 수행 | 이유 | 확인 기준의 표로 정리해.

어떤 역할을 다시 맡겨야 하는지와 별도 에이전트가 필요한지를 설명해.

단일 에이전트로 진행해. 외부 검색·하위 에이전트·설치·서버는 사용하지 마.
현재 폴더 밖이나 다른 A/B 폴더를 탐색하지 말고 입력 파일은 수정하지 마.
자료가 없으면 누락을 알려줘. 출력은 현재 폴더 out/ 안에만 저장해.
필요하면 out/을 만들고 마지막에는 변경 이유·실제 수정·미확인을 알려줘.
```

**예상 좋은 행동:** 조사 자료는 유지하고 설명의 난도·분량·문장 구조를 다시 검토한다. 쉬운 설명으로 바꾸면서 단위 정의·검사 한계를 훼손하지 않는다. HTML·번역·발행은 이번 범위에서 실행하지 않는다.

**설계 문장 해설:** “변경 조건과 영향”이 전체 재시작을 피할 근거를 만든다. “출처는 재사용하되 … 대조”는 재사용을 무검토 복사와 구별한다. “역할 이름이 있다는 이유만으로”는 편집·검토를 같은 에이전트가 순서대로 할 수 있음을 드러낸다.

**채점 풀이:** “모두 다시 한다”와 “아무 검토 없이 줄인다” 모두 이유가 부족하다. 수정 글이 쉬워졌다는 판단은 실제 용어 설명을 표시해 뒷받침한다. 새 독자가 생겼다는 이유만으로 새 사실 조사나 번역을 추가하면 범위를 넘는다.

**실패 대처:** 설명을 줄이다 “몇 개 검사가 모든 정확성을 보장하지 않는다”가 사라졌다면 한계를 복원한다. 분량 초과는 반복 표현부터 줄인다. 전체 조사 재실행이 제안되면 필요한 새 질문이 실제로 있는지 근거를 요구한다.

## S07. 내 방식 지침·인계 — 다음 AI가 정직하게 이어받게 하기

**공개 시점:** A가 만든 운영 지침과 상태 문서에서 “보고된 일”과 “직접 확인한 일”을 학생이 구분한 뒤.

**같은 입력:** `BRIEF.md`와 `CASES.md`의 **C6 가상 상태**. 원고·HTML 작성 보고만 있고 실제 `article.md`·`post.html`은 제공되지 않는다. 브라우저 확인·외부 게시·사용자 동의를 만들어내지 않아야 한다.

### 그대로 복사할 B

```text
현재 폴더의 BRIEF.md와 CASES.md의 C6을 읽어줘.
“AI가 만든 코드는 실행만 되면 믿어도 될까?” 블로그 작업을 위한
운영 지침 초안과 다음 세션 인계 문서를 만들어줘.
C6은 교육용 가상 상태다. 실제 이 세션에서 한 일과 섞지 마.
article.md·post.html은 작성됐다는 보고만 있고 이번 입력에 제공되지 않는다.
파일 존재·내용·브라우저 확인을 직접 완료했다고 쓰지 마.

현재 호스트가 Codex이면 out/AGENTS.md, Claude Code이면 out/CLAUDE.md를 만들어.
호스트를 확인할 수 없으면 out/AGENTS.md를 Codex용 초안으로 작성하고
호스트 미확인 상태를 알려줘. 입력 폴더 루트나 전역 지침에는 설치하지 마.
초안에는 다음 운영 규칙을 담아줘.
- 작업 전 발주서·현재 상태·관련 자료를 읽고 이번 범위와 완료 조건을 정한다.
- 사용자 목표는 존중하고 사실 주장은 자료와 독립 예상값으로 검토한다.
- 조사 자료·교육용 예시·실제 실행 결과를 구분한다.
- 입력을 보존하고 허용된 출력 위치에만 쓴다. 역할·도구·완료 조건을 정해 맡긴다.
- 생성·내용 확인·화면 확인·사용자 확인·외부 게시를 각각 기록한다.
- 작업 끝에 실제 변경·검증·미확인·다음 행동을 남긴다.
지속할 규칙과 이번 회차의 진행 상태를 섞지 마.

out/STATUS.md는 “C6 가상 인계 사례”라고 표시하고 아래 상태를 분리해.
원고·HTML: 작성 보고 있음, 파일 존재·내용은 미확인.
사람의 원고 출처 검토: 기록 없음.
브라우저 표시·링크: 미확인.
외부 게시·GitHub push: 수행하지 않음.
사용자 확인: 전달됐다는 설정만 있으며 열람·발행 동의는 미확인.
다음 행동: 파일 존재·내용을 먼저 확인하고, 없으면 누락을 보고한 뒤
원고 출처 대조와 가능한 환경에서의 브라우저 확인을 진행한다.

out/handoff.md에는 다음 세션에 복사할 완전한 재개 요청문을 써줘.
읽을 자료·현재 상태·첫 확인·중단 조건·기대 보고를 포함해.
새 세션이 파일을 실제로 받았는지부터 확인하도록 하고,
없으면 누락을 보고하며, 이전 완료 보고를 자동 신뢰하지 않도록 해.
외부 게시나 발행 동의 확인을 이번 작업이 대신했다고 쓰지 마.

현재 폴더 밖 탐색·입력 수정·검색·추가 에이전트·설치·서버·게시는 하지 마.
Skill·MCP·Plugin을 설치하거나 실제 지침을 자동 적용하지 마.
필요한 입력이 없으면 누락을 알려줘. 출력은 현재 폴더 out/ 안에만 저장해.
필요하면 out/을 만들고 마지막에는 생성한 초안 목록과 함께
“지침 로딩·자동 실행·다음 세션 재개 동작은 검증하지 않음”을 알려줘.
```

**예상 좋은 행동:** `out/AGENTS.md` 또는 `out/CLAUDE.md`는 운영 규칙, `STATUS.md`는 C6의 현재 상태, `handoff.md`는 다음 행동을 맡는다. 가상 인계 문서 작성과 실제 블로그 파일 검증을 구분한다.

**설계 문장 해설:** “작성 보고만 있고 … 제공되지 않는다”가 허위 확인을 판별할 핵심이다. “루트나 전역 지침에는 설치하지 마”가 평가용 초안이 뒤의 A/B 실행 조건을 바꾸지 않게 한다. “지침 로딩 … 검증하지 않음”이 Markdown 생성과 호스트 동작을 구별한다.

**채점 풀이:** 파일명을 `agent.md`로 쓰면 Codex용 요구를 충족하지 못한다. 정확한 이름이어도 `out/`의 초안이 실제로 자동 로드됐다고 인정하지 않는다. 브라우저·출처 검토·사용자 열람·외부 게시를 모두 완료로 쓴 상태 문서는 고쳐야 한다.

**실패 대처:** 초안이 현재 루트에 적용됐으면 원본 입력과 기존 지침을 보존하며 비교 환경을 다시 분리한다. 자동 적용된 조건에서 얻은 결과는 같은 조건의 A/B로 해석하지 않는다. 가짜 완료 기록은 C6 원문과 대조해 “보고 있음/미확인/수행 안 함”으로 바로잡는다.

**선택 확장:** 반복해 안정된 작성·검토 절차만 별도 Skill 초안의 후보로 정리할 수 있다. 기본 과제에서는 Skill 설치·호스트 로딩·MCP 연결을 수행하지 않는다. 파일을 작성했다고 반복 절차가 자동 실행되는 것은 아니다.

## 공통 채점표 — 네 축, 각 0~2점, 총 8점

이 표는 A 작성 전에 공개한다. 강사 문장을 그대로 썼는지보다 산출물과 학생 설명을 평가한다.

| 축 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 요구 충족 | 다른 주제·입력 사용 또는 핵심 산출물 누락 | 산출물은 있으나 분량·독자·필수 내용 일부 누락 | 해당 상황의 범위·입력·산출물을 실제 확인 |
| 근거 정확성 | 출처·실행·성과 수치를 꾸며냄 | 출처는 있으나 주장 연결·한계 구분 부족 | 주장과 자료가 맞고 사례·요약·미확인 구분 |
| 위임·범위 통제 | 무단 범위 확장 또는 실행하지 않은 위임을 완료 주장 | 경계는 있으나 의존 관계·실행 증거 부족 | 필요한 범위만 수행하고 실제 실행·미실행 설명 |
| 재작업과 설명 | 차이·원인·다음 행동 설명 없음 | 수정은 있으나 이유나 확인 방법 부족 | 차이를 근거로 설명하고 필요한 부분만 수정·확인 |

- S02 실제 위임을 못 했어도 이를 정직하게 기록한 점은 인정한다. 다만 **실제 하위 에이전트 수행 여부는 별도 체크**하며 문서만으로 충족 처리하지 않는다.
- S05 화면 확인, S07 지침 로딩도 같은 원칙이다. 정직한 “미확인”은 좋은 기록이지만 해당 검증을 완료했다는 증거는 아니다.
- 예: S04에서 네 오류와 결론을 교정했지만 출처 대응이 일부 빠졌고 수정 이유를 한 문장만 썼다면 `2+1+2+1=6점`으로 설명할 수 있다. 점수보다 빠진 근거와 다음 수정을 함께 적는다.
- 근거 없는 수치·실행·승인·발행 주장을 그대로 둔 산출물은 수정 전 발행 보류다. 높은 총점으로 허위 완료 기록을 상쇄하지 않는다.

## 강사 진행 요약과 비교 원칙

1. **발주 공개:** 입력·목표·도구 상한·산출물·채점표를 먼저 보여준다. B에만 유리한 숨은 조건을 만들지 않는다.
2. **A 먼저:** 학생이 무엇을 맡길지 결정하고 자작 요청문을 실행한다. 좋은 결과도 원래대로 보관한다.
3. **첫 결과 고정:** 최초 응답·산출물·관찰 기록을 남긴다. A/B 각각 보완 요청은 최대 1회이며 원응답과 구분한다.
4. **해당 B 공개:** 앞 상황의 해법을 다음 상황 정답처럼 누적하지 않는다. 새 세션·같은 고정 입력에서 B를 실행한다.
5. **직접 대조:** 요청문 차이→관찰된 행동 차이→산출물 증거를 연결한다. 시간·호출·표시 토큰은 실제 값만 기록하고 안 보이면 미확인으로 둔다.
6. **C 개선:** 학생이 A/B에서 필요한 문장을 선택해 자기 요청문 C를 쓴다. 바꾼 구절·예상 효과·검증 방법을 설명하고 필요할 때 다시 실행한다.
7. **연속 제작:** 비교가 끝나면 별도 `final/`에서 선택한 자기 프롬프트로 기획→조사→집필→검토→미리보기→인계를 이어간다. 이 결과를 고정 입력 A/B 비교와 혼합하지 않는다.

| 상황 | 강사가 꼭 확인할 관찰 증거 | 학생에게 남길 핵심 질문 |
|---|---|---|
| S01 | 완료 기준과 작업 사이의 선행 관계 | 어느 문장이 원고를 성급하게 만들지 않도록 했나? |
| S02 | 실제 하위 작업·대기·반환·총괄 대조 | 둘로 나눌 독립 범위와 통합 비용은 무엇인가? |
| S03 | 주장 옆 출처·교육용 제안·검증 한계 | 어느 주장까지 자료가 뒷받침하는가? |
| S04 | 네 오류와 잘못된 결론의 실제 교정 | 사용자 목표를 유지하며 어떤 사실을 고쳤나? |
| S05 | 내용 보존·브라우저 확인 기록·남은 미확인 | 파일 생성만으로 확인할 수 없는 것은 무엇인가? |
| S06 | 재사용·재수행 이유와 수정 원고 | 조건 변경이 어느 업무에만 영향을 주었나? |
| S07 | 작성 보고·존재 확인·사용자 확인 분리 | 다음 AI가 첫 번째로 직접 확인할 것은 무엇인가? |

**마무리 대사:** “B가 더 길어서 좋았다고 결론내리지 맙시다. 어떤 문장이 범위·근거·도구·재작업을 바꿨는지 실제 결과로 설명해봅시다. A가 더 잘했다면 그 이유도 남깁니다. 이번 소규모 관찰만으로 모든 모델·과제의 우열이나 특정 문장의 인과 효과를 확정할 수는 없습니다.”
