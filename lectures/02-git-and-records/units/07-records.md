# 07 · 작업 기록과 README 만들기

> [!NOTE]
> **PDF 연결 | 새로 추가**
> Git 작업 기록과 README 작성법은 원본에 없는 교육 내용이다. PDF 17~18쪽의 문제 정의·기준·피드백 흐름과 35~37쪽의 평가·반복을 문서로 남기는 활동으로 확장했다. 원문이 Git 또는 README를 권고했다는 뜻은 아니다. 평가 지표의 적용 범위 교정은 [보고서 검토](../../../research/report-review.md)를 따른다.

## 목표·준비·산출물

- 목표: 처음 보는 사람이 입력·검증·현재 범위를 찾고 작업을 이어갈 수 있게 쓴다.
- 준비: 자신의 Git 실습 저장소와 실제 diff·log·검증 메모. 프로그램 없는 경로도 가능하다.
- 산출물: 사건 하나의 작업 기록, 내용이 채워진 README, 짝의 재현·이해 점검 결과.
- 완료 기준: 자료에 없는 실행·성과·사용자 동의를 쓰지 않고 증거 위치를 연결한다.

## 개념 설명

커밋은 변경 단위를 남긴다. 작업 기록은 왜 바꿨고 어떤 방법으로 확인했는지를 남긴다. README는 처음 온 사람이 지금 무엇을 쓸 수 있는지 이해하도록 안내한다. 세 문서를 똑같이 길게 쓸 필요는 없다. 이미 있는 증거를 독자에 맞게 골라 연결한다.

작업 기록은 문제 → 관찰 → 선택 이유 → 실제 변경 → 검증 → 남은 일 순서로 쓴다. “에러가 나서 해결했다”보다 “README의 Mean이 2.5인데 입력을 환산한 평균은 2였다. 오류 커밋을 확인한 뒤 revert로 상쇄했다”가 재사용하기 쉽다. 이력의 실제 해시를 적으면 정확한 위치를 찾을 수 있다. 해시가 아직 없으면 상상의 값을 넣지 않는다.

README의 실행 방법은 현재 존재하는 결과물에 맞아야 한다. 이 Git 실습에는 분석 프로그램이 없다. 그러므로 `python analyze.py`처럼 없는 명령을 작성하지 않는다. Git 설치와 파일 확인, 손계산 검증을 안내한다. 이후 프로그램이 생기면 환경·명령·입력·출력·오류 처리를 실제 실행으로 확인한 뒤 갱신한다.

**작성 완료, 검증 완료, 사용자 확인**은 서로 다르다. 문서를 만들었어도 짝이 읽지 않았을 수 있다. “전달”은 “열람”이나 “동의”의 증거가 아니다. 기록에 실제 완료 상태와 남은 상태를 따로 적으면 다음 사람이 질문 없이도 이어가기 쉽다.

## 강사 진행 장면

### 장면 1 · 일주일 뒤의 자신에게 쓰기

**강사 발화:** “여러분이 일주일 뒤 돌아왔습니다. ‘단위 수정 완료’ 한 줄만 있으면 무엇을 다시 찾아야 할까요?”

**판서:** `입력 단위 / 출력 단위 / 바꾼 줄 / 이유 / 확인 근거`를 적는다.

**예상 학생 답:** “무엇을 바꿨고 어느 단위가 맞는지 다시 조사해야 합니다. CSV 헤더와 최종 문장, 손계산을 남겨야 합니다.”

### 장면 2 · 미래 기능 지우기

**강사 발화:** “README에 ‘CSV를 자동 분석해 그래프를 생성한다’고 적혀 있습니다. 지금 파일 목록에서 그 기능을 실행할 수 있나요?”

**화면:** `git ls-files`의 네 파일과 README 초안을 나란히 둔다.

**예상 학생 답:** “현재는 합성 CSV와 문서만 있습니다. 자동 분석과 그래프는 이후 계획으로 분리해야 합니다.”

### 장면 3 · 짝에게 말하지 않고 전달

**강사 발화:** “이제 짝에게 저장소와 README를 줍니다. 설명을 덧붙이지 않고 입력 단위와 평균 검증법을 찾게 하세요. 막힌 부분이 문서 보완 지점입니다.”

**화면:** 아래 완성 예시를 읽게 한 뒤 학생 README와 비교한다. 실제 프로그램이 없다면 프로그램 실행을 평가하지 않는다.

**예상 학생 답:** “voltage_mv는 mV이고 1000으로 나누면 V입니다. 세 값의 평균은 2V입니다.”

### 장면 4 · 미확인을 기록하기

**강사 발화:** “AI가 README를 만들었고 내가 열었습니다. 그러면 동료 재현까지 완료인가요? 확인하지 않은 상태도 정확한 정보입니다.”

**판서:** `문서 작성 완료 / 로컬 내용 확인 / 짝 점검 미수행 / GitHub 미수행`을 나눈다.

**예상 학생 답:** “내가 실제 확인한 범위만 완료로 적고 나머지는 미수행으로 남깁니다.”

## 함께 풀 사례 · 내용이 채워진 README

다음은 **Git 기초 실습 저장소에 넣을 수 있는 교육용 완성 예시**다. 학생 수행 결과를 대신 증명하지 않는다. 단원 5까지의 파일 상태를 기준으로 하며, 자신의 수행 범위가 다르면 해당 문장을 수정한다. 기존 README를 확장하는 시점은 앞선 연속 실습을 마친 뒤다.

````markdown
# Measurement notes

## 목적과 현재 상태

합성 측정 CSV를 사용해 Git의 변경 기록·복구·병합을 연습하는 저장소다.
현재 자료는 CSV와 문서다. 자동 분석 프로그램과 그래프 생성 기능은 없다.

Unit: input mV, output V
Mean: 2
Status: reviewed
Source: synthetic sample

reviewed는 이 수업에서 정한 샘플 손계산 검토 상태다.
프로그램 테스트나 동료 승인 완료를 뜻하지 않는다.

## 파일

- samples.csv: 시간과 전압을 담은 합성 입력 3행.
- README.md: 자료 목적·단위·확인 방법.
- scratch.txt: 복구 연습용 파일. 분석 입력으로 사용하지 않는다.
- .gitignore: 비밀 설정·환경 폴더·임시 출력의 제외 규칙.
- outputs/demo.txt: 만들어 둔 경우에만 존재하는 임시 출력 예제.
  Git 추적에서 제외되므로 clone한 복사본에 없어도 정상이다.

## 입력과 예상값

```csv
time_ms,voltage_mv
0,1000
1000,2000
2000,3000
```

시간은 ms, 전압은 mV다. 각각 1000으로 나누면 초와 V가 된다.
변환 시간은 0, 1, 2초, 변환 전압은 1, 2, 3V다.
표본 수 3, 평균 2V, 최솟값 1V, 최댓값 3V가 손계산 예상값이다.

## 확인 방법

Git과 텍스트 편집기를 준비하고 저장소 폴더에서 실행한다.

```shell
git --version
git status
git ls-files
git log --oneline -5
```

samples.csv를 열어 세 행과 열 이름을 확인한다.
평균은 (1000 + 2000 + 3000) / 3 / 1000 = 2V로 대조한다.
README의 Mean과 Unit을 확인한다. 명령 성공만으로 계산이 맞다고 판단하지 않는다.

## 범위와 한계

CSV 자동 읽기, 누락값 검사, 역순 시간 검사, 그래프 생성은 구현하지 않았다.
다른 데이터도 자동 처리된다고 보장하지 않는다. 실제 장비 데이터도 사용하지 않았다.
GitHub 인증과 PR 수행 여부는 각자의 작업 기록에서 확인한다.
.gitignore는 이미 추적된 파일이나 과거 커밋을 삭제하지 않는다.

## 역할과 참고

이 문서는 강의용 작성 예시다. 학습자의 실제 수행·AI 도움은 작업 기록에 별도로 남긴다.
수업의 합성 CSV와 Git 공식 문서를 참고한다.
Git 변경 기록: https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository
````

README를 작성한 뒤 `git diff -- README.md`로 기존 단위·평균·출처가 보존됐는지 읽는다. staged diff와 손계산을 확인한 뒤 문서 목적의 커밋을 만든다. 실제 실행한 뒤에만 작업 기록의 수행 항목에 쓴다.

## 작업 기록 완성 예시 · 사실과 예시의 경계

아래는 **단원 5 시나리오를 정상 수행한 경우의 교육용 기록 예시**다. 현재 학생이 수행했다는 뜻이 아니다. 실제 제출은 자신의 해시·관찰·역할로 작성한다.

> **작업명:** 입력·출력 전압 단위 설명 충돌 해결.
>
> **문제와 목표:** main은 입력 mV, docs/units는 출력 V를 같은 줄에 적었다. 두 설명을 보존하고 독자가 단위를 구별하도록 한다.
>
> **관찰:** README의 Unit 줄 병합이 충돌했다. CSV 열 이름은 voltage_mv이고 샘플은 1000·2000·3000이다.
>
> **판단:** 어느 한쪽 전체 선택은 다른 단위 설명을 잃는다. Unit: input mV, output V로 통합한다.
>
> **변경:** README의 충돌 구간과 표시를 최종 한 줄로 정리한다. 커밋 메시지는 docs: reconcile input and output unit descriptions다. 이 교재는 학생의 실제 커밋 해시를 제공하지 않는다.
>
> **예시의 확인 결과:** diff --check 통과, 평균 2V 손계산, Mean·Status·Source 보존, 병합 커밋 뒤 clean 확인을 기록하는 상황이다. 제출자는 실제 출력과 대조해야 한다.
>
> **역할:** 강의가 충돌 시나리오와 해결 후보를 제공했다. 학생이 직접 판단·실행한 범위와 AI의 추가 도움은 본인 기록에서 명시한다.
>
> **상태:** 교육용 문서 예시 작성 완료. 학생 실행·짝 검토·GitHub 반영은 이 예시로 확인할 수 없다.
>
> **다음:** 실제 수행 자료를 연결하고 짝에게 단위와 검증법을 설명하게 한다.

## 학생 활동·풀이 기준

1. 복구 또는 충돌 중 실제 수행한 사건 하나를 고른다. 수행하지 않았다면 먼저 연습하거나 미수행 초안으로 표시한다.
2. log·show·CSV에서 근거를 찾아 실제 작업 기록을 작성한다.
3. README에 목적·파일·입력·확인법·한계·역할을 채운다. 위 예시를 그대로 자신의 성과로 복사하지 않는다.
4. 짝에게 파일만 전달하고 원본 위치·입력 단위·예상값·현재 기능·미검증을 찾게 한다.
5. 짝이 실제 답한 내용과 막힌 지점을 기록한다. 읽었는지 확인되지 않았다면 “열람 미확인”으로 둔다.
6. 필요한 문장을 고친 뒤 diff와 링크를 확인하고 검토된 문서를 기록한다.

**통과 답:** “samples.csv의 voltage_mv는 mV, 평균은 2V, 현재 자동 프로그램 없음, GitHub 수행 여부는 작업 기록 확인”이 문서만으로 드러나야 한다. 없는 실행 명령·성과가 있으면 수정한다.

## 질문·다음·출처

- **기록을 길게 써야 하나요?** 다음 판단에 필요한 증거와 이유가 빠지지 않으면 된다. AI 대화 전체를 붙일 필요는 없다.
- **AI가 쓴 문서는 내 기여가 아닌가요?** 문구 작성 도움과 본인의 판단·검증을 구분해서 설명한다.
- **미완성을 쓰면 불리한가요?** 현재 범위를 정확히 쓰면 독자의 오해와 재작업을 줄일 수 있다.
