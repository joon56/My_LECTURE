# 3. 모호한 과제를 작업 명세로 바꾸기

[이전: 검증](02-verification.md) · [전체 설계](../plan.md) · [다음: 프롬프트](04-prompting.md)

## 학습 목표와 수업 준비

학생은 “측정 데이터 분석해 와”를 다른 사람이 구현·검증할 수 있는 작업 명세로 바꾼다. 모르는 정보를 질문과 임시 가정으로 구분하고, 작업 분해 뒤 선행 관계를 표시한다. 선수 지식은 CSV 열·단위, 단원 2의 예상값 검사다. 학생 산출물은 `SPEC.md` 한 장과 작업 의존 관계 그림이다. 문서 길이보다 **서로 다른 구현을 같은 기준으로 판정할 수 있는지**를 평가한다.

> [!NOTE]
> **PDF 연결 | 활용 / 교정 후 활용**
>
> 도입에는 원본 15~18쪽의 명확성·문제 정의를, 장면 2에는 17쪽 표 2와 그림 2의 문제 정의→기대치→위임→피드백→반복을 놓는다. 각 단계 아래 학생이 만들 파일·예상값·관찰 기록을 적는다.
>
> 장면 3에서 19~22쪽의 MECE·로직 트리·위임 기준을 활용한다. **MECE는 중복·누락을 점검하는 분해 원칙이다. 실행 독립성까지 보장하지 않는다.** 데이터 검증 뒤 계산이 가능한 반례를 함께 그린다.
>
> **추가 내용:** 정상·오류 입력 계약, 중요 가정의 결정권자, 변경 범위, 복구 가능성은 실무 명세로 확장했다. 원본 18쪽의 문제 정의는 “혼자 완벽하게 정리해야 AI를 쓸 수 있다”로 가르치지 않는다. AI와 빠진 질문을 찾으며 명세를 함께 다듬을 수 있다.

## 개념: 작업 명세는 서로 다른 머릿속 그림을 맞추는 문서다

“분석 프로그램”을 들으면 어떤 사람은 그래프를, 다른 사람은 통계 표를 떠올린다. “이상한 값 처리”도 삭제·보간·경고 중 어느 것인지 알 수 없다. 명세는 구현 전에 이 차이를 드러낸다. 적어도 **목적, 입력, 출력, 계산 규칙, 제약, 완료 기준**이 있어야 한다. 화면 색상 같은 선호는 뒤로 미룰 수 있어도 단위·평균 계산 대상·결측 처리처럼 숫자를 바꾸는 결정은 숨기면 안 된다.

모르는 항목을 다 질문할 필요도 없다. 질문의 기준은 답이 결과나 위험을 얼마나 바꾸는지다. 원자료 단위를 모르면 먼저 확인해야 한다. 연습용 출력 파일명은 충돌 없는 이름을 임시로 정하고 표시할 수 있다. 실제 장비 제어 여부나 외부 공개 범위는 수업용 데이터 처리와 영향이 다르므로 같은 권한으로 추정하지 않는다.

**가정**은 모르는 것을 사실로 덮는 문장이 아니다. “이번 실습은 합성 데이터이며 각 행의 시간은 ms다”처럼 범위와 검증 방법을 붙인다. 사용자가 합의하지 않은 처리 정책은 `수업 예제의 선택` 또는 `확인 필요`로 표시한다. 이후 답이 달라졌으면 영향을 받는 코드·검사도 함께 수정한다.

작업 분해는 기능 이름만 나열하는 것으로 끝나지 않는다. 각 단계에 입력·출력·선행 조건이 있어야 한다. `읽기 → 검증 → 변환 → 요약`은 서로 다른 책임이지만 실행은 연결돼 있다. 그래프와 요약은 둘 다 변환된 자료를 사용하므로 그 이후에는 나눠 수행할 수 있다. MECE 분해와 병렬 실행 여부를 별도의 질문으로 판단한다.

위임 판단은 검증 가능성·반복성·문서화 가능성에 **오류의 영향과 복구 가능성**을 더해 본다. 단위 변환 코드를 작성시키는 일은 작은 정답으로 검사할 수 있다. 센서 고장 원인을 단정하거나 실험값을 삭제하는 일은 관측 조건과 담당자의 기준이 필요하다. 반복되는 정해진 계산은 검증된 코드로 수행하고, 과학적 해석은 근거를 검토한다.

## 강사 진행 대본

### 장면 1 — 한 요청에서 서로 다른 프로그램이 나온다

**판서:** `측정 데이터 분석해 와`.

> “여기서 완료했다고 말하려면 무엇이 있어야 할까요? 그래프만 있어도 될까요? 평균만 있으면 될까요? 지금 의견이 갈리는 이유는 여러분의 실력이 아니라 요청에 기준이 빠져 있기 때문입니다.”

**행동:** 학생 답을 입력·출력·처리 규칙으로 묶는다. 강사는 즉시 정답 양식을 주기보다 `단위`와 `결측 처리`가 빠졌는지 확인한다.

**예상 질문:** “아직 뭘 만들지 모르는데 명세부터 쓸 수 있나요?”

**답변:** “완성 문서가 아니라 질문 목록부터 시작하면 됩니다. AI에게도 누락을 찾게 할 수 있습니다. 결정되지 않은 항목을 숨기지 않는 것이 첫 단계입니다.”

### 장면 2 — 기대치는 결과를 본 뒤 바꾸지 않는다

**화면:** PDF 17쪽 워크플로우와 3행 CSV.

> “두 번째 단계가 기대치 작성입니다. 코드가 내놓은 값을 보고 정답을 정하면 같은 오류를 복사할 수 있습니다. 지금 손으로 1·2·3 V와 평균 2 V를 적겠습니다. 구현 전에 확인 기준을 만든 겁니다.”

**판서:** `입력 예 / 예상 결과 / 오류 입력의 기대 동작`.

**예상 질문:** “정답을 모르면 AI를 못 쓰나요?”

**답변:** “모든 답을 미리 알 필요는 없습니다. 작은 부분의 정답, 물리 단위, 합계 관계, 참고 실험 등 확인할 수 있는 기준부터 마련합니다. 기준이 전혀 없으면 완료를 단정할 수 없습니다.”

### 장면 3 — 쪼갠 작업에 화살표를 붙인다

> “읽기와 평균 계산은 이름이 겹치지 않습니다. 그래도 읽기가 실패하면 평균 계산은 진행할 수 없습니다. 중복 없이 나눴다는 것과 서로 기다릴 필요가 없다는 것은 다릅니다.”

**판서:** `CSV 읽기 → 필수 열·값 검증 → 단위 변환 → 평균`, 변환에서 `그래프`로 갈라지는 화살표.

**학생 활동:** 각 화살표에 전달되는 자료를 적는다. `파일` 대신 `검증된 (시간, 전압) 행 목록`처럼 받는 쪽에서 이해할 수준으로 쓴다.

### 장면 4 — AI가 정해도 되는 선택을 나눈다

> “변수 이름과 반복문 형태는 AI가 정해도 됩니다. 누락값을 0으로 바꿀지는 평균을 바꾸므로 명세에 있어야 합니다. 모든 줄을 허락받게 할 필요는 없지만 결과를 바꾸는 판단은 드러나야 합니다.”

**예상 질문:** “명세 밖에서 더 좋은 기능을 만들어주면요?”

**답변:** “추가 가치와 검증 부담을 따로 봅니다. 이번 완료 기준을 먼저 충족하고 필요하면 다음 작업으로 제안합니다.”

## 완성 명세 예제

아래는 합성 CSV 수업의 **완성된 예시 명세**다. 실제 연구실 요구사항을 확인했다는 뜻은 아니다.

```markdown
# SPEC: 합성 전압 CSV 요약

## 목적
세 측정값의 단위 변환과 산술평균을 재현 가능하게 확인한다.

## 입력
- UTF-8 CSV 파일. 첫 행은 time_ms,voltage_mv.
- time_ms는 ms, voltage_mv는 mV. 각 값은 유한한 숫자다.
- 이번 범위는 숫자 데이터 행 1개 이상이다.
- 행의 순서를 바꾸지 않는다.

## 출력
- 콘솔에 행 수, 각 행의 time_s·voltage_v, mean_voltage_v를 출력한다.
- 원본 파일을 수정하지 않는다.

## 처리 규칙
- time_s = time_ms / 1000.
- voltage_v = voltage_mv / 1000.
- mean_voltage_v는 모든 데이터 행 전압의 산술평균이다.
- 누락값·비수치·필수 열 누락·데이터 행 없음은 오류로 알리고 중단한다.
- 오류가 있는 파일에서 일부 행만으로 정상 평균을 출력하지 않는다.
- 보간·이상치 제거·센서 고장 판정은 이번 범위에 포함하지 않는다.

## 구현 제약
- 수업에서 준비한 Python 환경과 표준 라이브러리를 사용한다.
- 장비 연결, 외부 업로드, 추가 패키지 설치는 필요하지 않다.

## 완료 기준
- 기본 입력의 시간은 0,1,2 s, 전압은 1,2,3 V, 평균은 2 V다.
- 500 mV 한 행을 넣으면 평균은 0.5 V다.
- 헤더만 있는 파일과 누락값 파일에서는 원인을 알리고 중단한다.
- 실행 명령·입력·실제 출력·예상값 비교를 기록한다.
```

기본 입력은 `0,1000`, `1000,2000`, `2000,3000` 세 행이다. **예상 출력과 이유:** 각각 1,000으로 나누므로 시간 0·1·2 s, 전압 1·2·3 V다. 합 6 V를 3으로 나누면 2 V다. 한 행 500 mV 사례는 세 행 전용으로 하드코딩한 구현을 걸러낸다. 오류 사례는 프로그램이 조용히 데이터를 버리는지 검사한다.

표시 소수점 개수는 이 명세에서 핵심이 아니다. `2`와 `2.0`을 같은 수치로 볼 수 있다. 엄격한 문자열 비교가 필요하다면 자릿수·구분자까지 별도 계약으로 정한다. 그래프가 필요해지는 다음 단계에는 축 이름·단위·저장 위치도 추가한다.

## 학생 실습: 빠진 조건을 찾아 명세를 고친다

**제시 요청:** “온도랑 전압 들어 있는 파일을 정리하고 이상한 값은 빼고 예쁘게 그래프 그려줘.”

1. 이 요청에서 확인된 목표와 미확정 사항을 나눈다.
2. 결과를 크게 바꾸는 질문을 세 개 먼저 고른다.
3. 답을 기다리지 않아도 만들 수 있는 골격을 적는다. 미확정 단위나 삭제 기준을 사실처럼 채우지 않는다.
4. 이번 연습에서는 강사가 `전압만 처리, mV, 삭제 금지, 결측이면 중단`이라는 조건을 제공한다. 그 조건으로 명세를 완성한다.
5. 읽기·검증·변환·요약·그래프의 입력·출력·의존 관계를 그린다.
6. 짝이 명세만 읽고 기본 입력·오류 입력의 예상 동작을 써 본다. 둘의 답이 다르면 애매한 문장을 수정한다.

**풀이 예:** 우선 질문은 실제 파일 구조와 단위, 이상한 값의 판정 근거·처리 권한, 필요한 최종 산출물이다. 기다리는 동안 제출 형식과 입력 예제 칸을 준비할 수 있다. 데이터 열이나 삭제 임계값을 임의로 정하면 안 된다. 그래프와 평균은 변환 결과 이후로 연결하며 검증 실패 시 둘 다 정상 산출물을 만들지 않는다고 명시한다.

**평가 10점:** 입력·단위 2점, 출력·사용 목적 2점, 오류 정책 2점, 독립된 완료 기준 2점, 가정·의존 관계 2점. 문서가 길어도 단위와 오류 정책이 없으면 보완한다.

## 자주 묻는 질문과 완료 기준

- **“명세를 쓰면 변경하면 안 되나요?”** 새 정보에 맞춰 변경할 수 있다. 무엇이 바뀌었고 예상값·코드에 어떤 영향이 있는지 기록한다.
- **“MECE면 모든 기능을 따로 맡기면 되나요?”** 데이터 계약과 선행 관계를 확인한 뒤 결정한다. 공유 파일을 동시에 수정하는 문제도 별도로 본다.
- **“AI가 질문을 너무 많이 하면요?”** 결과에 큰 영향을 주는 질문부터 요청한다. 되돌릴 수 있는 사소한 선택은 근거를 적고 진행하게 한다.

다른 학생이 정상·오류 입력의 완료 여부를 판단하고, 작성자가 중요한 가정을 설명하면 완료다. 다음 [단원 4](04-prompting.md)에서는 이 명세에서 이번 행동에 필요한 부분을 뽑아 정확한 요청문으로 만든다.
