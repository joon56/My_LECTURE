# 공통 발주서 · 기술 블로그 제작사

자료 버전: 2026-10-04. 학생 A와 강사 B에게 **같은 발주서·자료·제한**을 제공한다. 이 파일은 AI가 따라야 할 실습의 작업 조건이다.

## 주제와 독자

- 공통 주제와 최종 제목: **AI가 만든 코드는 실행만 되면 믿어도 될까?**
- 독자: AI로 프로그램 과제를 해본 공대 1~2학년. 한국어.
- 목적: 독자가 실행 성공·요구 충족·검증을 구별하고 생성된 코드를 확인할 행동 세 가지를 설명할 수 있게 한다.
- 학생은 제작사의 대표 겸 편집장이다. 작업 분배·근거 선택·수정·발행 여부를 판단한다. 에이전트는 맡은 범위에서 자료를 읽고 작업을 수행한다.
- 모든 학생이 같은 주제를 다룬다. 회사 이름·문체는 자유지만 주제·독자·검증 기준은 아래와 같이 고정한다.

## 최종 글과 결과물

- 본문은 공백 포함 1200~1800자를 목표로 한다. 제목·코드·참고문헌은 제외한다. 편집기에서 해당 본문만 선택해 글자 수를 확인한다. 초과·미달이면 이유와 조정 여부를 기록한다.
- 소제목 3~5개, 단위 변환 반례 하나, 독자가 해볼 확인 행동 세 가지, 적용 한계, 출처 링크를 넣는다.
- 글에서 다루는 사실은 SOURCES.md의 S1~S3와 CASES.md의 교육용 사례를 근거로 한다. 자료의 적용 범위를 넘어선 일반화를 피한다.
- 참고문헌 목록만 붙이지 말고 어떤 주장에 어떤 자료가 연결되는지 본문에서 표시한다.
- 최종 제작 폴더에는 article.md, sources.md, post.html, review.md, STATUS.md와 사용한 자기 프롬프트 기록을 남긴다.
- HTML은 로컬에서 열 수 있는 한 파일이다. CSS는 파일 안에 두고 외부 이미지·폰트·스크립트·서버·패키지를 추가하지 않는다. 디자인은 제목·본문·코드·출처의 가독성에 집중한다.
- 기사 파일 작성, 브라우저 확인, 외부 게시 상태는 각각 기록한다. 로컬 HTML 완성만으로 블로그 업로드 완료라고 쓰지 않는다.

## 자료와 권한

- 기본 비교는 BRIEF.md, SOURCES.md, CASES.md 세 파일만 읽는다. 다른 조건의 결과나 강사용 교안을 읽히지 않는다.
- SOURCES.md는 공식 문서 위치와 교재 요약이다. 원문 전문이나 실제 웹 조회 기록이 아니다. 원문을 직접 열지 않았다면 “제공 자료 검토”라고 보고한다.
- 온라인 원문 대조는 최초 A/B 비교를 저장한 뒤 별도 검증으로 수행한다. 비교 당시의 제공 자료 검토와 이후 원문 열람을 나누어 기록한다. 한쪽만 원문을 읽은 결과는 프롬프트만의 비교로 해석하지 않는다.
- 입력 세 파일은 보존한다. 현재 A 또는 B 작업 폴더의 out/에만 결과를 쓴다. out/은 빈 폴더로 준비하며, 없으면 새로 만든다.
- 도구 설치·계정 설정·외부 업로드·Git push는 이 비교 작업의 범위에 없다. 필요한 조건이 없으면 그 지점과 대체 방법을 보고한다.

## 상황별 동일 입력과 산출물

각 상황은 새로 시작한다. 앞 상황 A/B의 결과가 다음 상황의 입력이 되지 않는다. 아래 고정 자료가 비교의 출발점이다.

| 상황 | 작업·입력 | 필수 결과 |
|---|---|---|
| S01 | 발주·기획 / BRIEF | out/plan.md: 독자·목적·완료 기준·작업 분해·선행 관계·위임 이유 |
| S02 | 위임·자료 조사 / SOURCES S1~S3, CASES C1 | out/evidence.md, out/delegation.md: 주장·출처·한계와 실제 위임 기록 |
| S03 | 원고 작성 / CASES C2의 동일 근거표 | out/article.md: 공통 조건에 맞는 한국어 글 |
| S04 | 사실 검토·동조 대응 / CASES C3의 결함 원고와 의뢰 문장 | out/review.md, out/corrected.md: 주장별 판정·근거·수정안 |
| S05 | 디자인·미리보기 / CASES C4의 동일 짧은 원고 | out/post.html, out/preview-check.md: 내용 보존·로컬 화면 확인 상태 |
| S06 | 조건 변경 / CASES C4+C5 | out/revision-plan.md, out/revised.md: 재사용·재실행 판단과 수정 글 |
| S07 | 운영 지침·인계 / CASES C6 | out/AGENTS.md 또는 out/CLAUDE.md, out/STATUS.md, out/handoff.md |

S04~S06의 고정 짧은 원고는 비교용 입력이다. S04는 주장별 교정에 집중한 짧은 수정문이며 최종 글 분량·소제목 개수를 요구하지 않는다. S05에서 S03의 글자 수 목표를 맞추려고 원문을 늘리지 않는다. S06은 변경된 글자 수 조건을 따른다. 마지막 연속 제작에서 최종 글의 조건을 적용한다.

최종 연속 제작에서는 실제 앞 단계 결과를 다음 입력으로 쓴다. 이때 작업 루트는 final/이며 결과물은 out/, 학생 기록은 notes/, 현재 상태와 선택한 도구 지침은 final/ 바로 아래에 둔다. A/B 비교의 고정 입력 규칙을 연속 제작에 그대로 적용하지 않는다. 게시용 export/는 사람이 검토한 세 파일만 복사한다.

## 같은 조건에서 비교하는 규칙

1. 강사 프롬프트를 보기 전에 학생이 A 요청문을 직접 쓰고 원응답·산출물을 보관한다.
2. B는 같은 입력 사본·동일 도구/모델 설정·새 대화에서 시작한다. A 결과를 읽히지 않는다. 공통 지침·메모리 차이는 기록한다.
3. 처음에는 A/B 각각 최초 응답을 비교한다. 보완 요청은 각 조건 최대 1회, 별도 기록한다. 원하는 결과만 골라 남기지 않는다.
4. S02는 A/B 모두 총괄 1개와 실제 하위 에이전트 최대 2개를 사용한다. 위임 비교에서는 같은 실행 방식을 선택한다. 다른 상황은 총괄 하나로 시작한다.
5. S02에서 두 하위 작업을 실행할 수 있으면 둘을 사용해 분담을 비교한다. 학생 A는 범위 나누기를 직접 설계한다. 추가·재귀 하위 에이전트는 만들지 않는다. 역할당 조사 응답은 핵심 12줄 안팎으로 제한한다.
6. 두 에이전트의 읽기 범위는 달라도 쓸 결과 파일을 충돌시키지 않는다. 기본은 하위가 읽기·보고만 하고 총괄이 파일을 저장하는 방식이다.
7. 지원되지 않으면 A/B 모두 별도 대화 두 개를 사람이 중계한다. 이 결과는 “수동 역할 분담”이며 실제 하위 에이전트 실행과 구별한다.
8. 소요 시간·호출 횟수·표시된 토큰 사용량·추가 질문·수정량을 기록한다. 사용량이 표시되지 않으면 미확인이다. 글자 수를 토큰 비용으로 환산하지 않는다.
9. B가 항상 더 좋다고 가정하지 않는다. A가 더 적은 작업으로 같은 기준을 만족하면 그 점을 기록한다. 작은 수업 비교는 일반적인 성능 순위나 특정 문장의 인과 효과를 증명하지 않는다.

## 공개 평가 기준

각 상황을 네 축으로 평가한다. 축마다 0=근거 없음/중대한 미충족, 1=부분 충족, 2=근거로 충족 확인. 총 8점이다.

- 요구 충족: 해당 상황의 입력·범위·산출물·독자 조건을 따랐는가?
- 근거 정확성: 주장과 자료가 맞고 미확인·교육용 사례가 구별되는가?
- 위임·범위 통제: 필요한 일만 수행하고 역할·의존 관계·권한·실제 실행을 설명하는가?
- 재작업과 설명: 수정 이유·다음 행동이 구체적이며 학생이 차이를 설명할 수 있는가?

별도 에이전트를 쓰지 않는 상황에서도 “위임·범위 통제”는 평가한다. 에이전트 개수를 늘려 점수를 얻지 않는다. 근거 없는 수치·실행·승인·발행 주장을 그대로 둔 산출물은 수정 전 발행 보류다. 미실행을 정직하게 보고한 것과 해당 동작을 실제 완료한 것은 별개의 성취다.
