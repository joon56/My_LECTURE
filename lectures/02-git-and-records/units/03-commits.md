# 03 · 변경을 읽고 의미 있게 커밋하기

> [!NOTE]
> **PDF 연결 | 새로 추가**
> 원본 PDF에는 diff·커밋 단위·.gitignore를 설명하는 직접 대응 내용이 없다. 이 단원은 AI가 만든 변경까지 사람이 검토하고 이력에 남기도록 강사가 새로 구성했다. 기술 근거와 교육 제안을 구분한다.

## 목표·강의 준비·핵심 요점

- 목표: status와 두 diff를 읽고 한 목적의 변경만 커밋한다.
- 강의 준비: 단원 2의 세 영역과 두 diff. 강사의 예시 커밋을 읽는다.
- 핵심 요점: 커밋 목적·실제 변경·검증 근거, 추적 파일과 ignore 규칙의 한계.

## 개념 설명

커밋 단위는 파일 수로 정하지 않는다. 평균 계산 오류를 고치면서 코드·검증 예제·README를 함께 바꿨다면 하나의 목적일 수 있다. 같은 파일 안에서도 제목 변경과 계산 오류 수정은 서로 다른 목적일 수 있다. 이 수업에서는 파일 전체를 선택하는 기본 작업을 먼저 익히고, 일부 줄만 고르는 기능은 심화로 남긴다.

커밋 전 읽을 것은 **실제 diff**다. AI가 “단위 설명만 고쳤다”고 말해도 diff에 입력값 변경이 섞여 있을 수 있다. 의도와 변경 내용을 대조해야 한다. diff의 `-`는 이전 내용, `+`는 새 내용이다. `---`와 `+++`는 비교 파일 표기이므로 본문 줄 삭제·추가와 구분한다. 줄 앞 기호만 세지 말고 의미를 읽는다.

`git diff`가 비어 있는 것은 커밋 준비 완료의 증거가 아니다. staged 변경은 `git diff --staged`로 확인해야 하며, 새 untracked 파일의 내용은 별도로 읽는다. 따라서 순서는 status → 파일 검토 → 일반 diff → 선택 add → staged diff → 검증 → commit → status·log다.

메시지는 나중에 이력을 찾을 사람을 위한 설명이다. `수정`, `최종`, `AI가 해줌`은 원인을 찾기 어렵다. `docs: mark sample review complete`처럼 대상과 변화가 드러나면 낫다. `docs:`, `fix:`, `feat:`는 팀이 정할 수 있는 관례다. Git 자체가 요구하는 접두어는 아니다. 메시지에 실행하지 않은 테스트를 통과했다고 쓰지 않는다.

`.gitignore`는 추적하지 않는 파일 가운데 무시할 패턴을 지정한다. 디스크 파일을 지우지 않고, 이미 추적 중인 파일이나 과거 이력을 제거하지도 않는다. 소스·설명·작은 합성 샘플은 기록할 가치가 있다. 환경 폴더·임시 결과는 다시 만들 수 있는지 판단해 제외한다. 실제 연구 원자료와 검증 증거는 재현에 필요한 보관 위치·버전·조건을 별도로 정한다.

## 강사 진행 장면

강사가 설명·판서·시연한다. 학생은 상태와 의미를 읽는다. 명령 따라하기·파일 수정·제출은 8단원 강의를 마친 뒤 [통합 실습](../practice.md)에서 진행한다.

### 장면 1 · AI의 보고와 diff 대조

**강사 발화:** “AI가 ‘README만 정리했습니다’라고 했습니다. 그런데 status에는 samples.csv도 바뀌었다고 나옵니다. 무엇부터 확인할까요?”

**판서:** `요청: 설명 개선 / 관찰: CSV 변경 / 판단: 값 변경 이유 확인`을 나눈다.

**예상 학생 답:** “CSV diff를 확인하고 요청과 관련 있는지 판단합니다. 설명 문장만 믿고 전부 add하지 않습니다.”

**이어갈 설명:** “AI 설명은 검토할 단서입니다. 실제 변경의 증거는 파일과 diff입니다. 원치 않는 변경을 발견하면 내용을 보존한 채 이유와 처리 방법부터 확인합니다.”

### 장면 2 · 커밋 이름 고르기

**강사 발화:** “README의 draft를 reviewed로 바꿨습니다. ‘최종 수정’과 ‘샘플 검토 상태를 reviewed로 기록’ 중 한 달 뒤 찾기 쉬운 것은 무엇인가요?”

**화면:** 강사 시연 저장소의 두 상태 커밋을 log와 show로 비교한다.

**예상 학생 답:** “바뀐 대상과 결과가 있는 메시지입니다. 프로그램 구현이나 테스트를 했다고 쓰면 안 됩니다.”

### 장면 3 · 무시된 파일은 어디로 갔나

**강사 발화:** “outputs/demo.txt를 만들었는데 status에는 안 보입니다. Git이 파일을 삭제했을까요?”

**화면:** 편집기에서 파일이 존재함을 보여주고 `git check-ignore -v outputs/demo.txt`를 실행한다.

**예상 학생 답:** “.gitignore의 outputs/ 규칙에 해당해서 상태 목록에서 제외됐습니다. 실제 파일은 남아 있습니다.”

### 장면 4 · 커밋 직전 검토 관점

**강사 발화:** “검토자는 staged diff에서 이번 변경 목적과 검증 방법을 읽습니다. 목적이 두 개라면 커밋 구성을 다시 생각할 이유가 됩니다.”

**판서:** `포함 파일 / 변경 의미 / 독립 확인 / 미확인` 네 항목을 적는다.

**예상 학생 답:** “README의 상태 문구만 바뀌었습니다. 샘플 평균은 손계산했고 프로그램은 실행하지 않았습니다.”

## 읽는 사례 · 기록 대상과 임시 결과

강사 시연의 추적 파일은 README.md, samples.csv, scratch.txt, .gitignore다. `.gitignore`에 `outputs/`가 있으면 이후 만든 `outputs/demo.txt`는 기본 status에 나타나지 않는다. 파일은 디스크에 남는다.

```shell
git check-ignore -v outputs/demo.txt
git ls-files
```

첫 명령은 적용된 무시 규칙을, 둘째는 추적 파일을 보여준다. “status에서 안 보인다”와 “삭제됐다”를 구분하는 근거다.

| 변경 제안 | 판단 근거 |
|---|---|
| README의 입력 단위 명시 | 설명을 고치는 목적에 맞음 |
| 평균을 맞춰 보이도록 CSV 값을 바꾸기 | 입력과 검증 기준을 훼손함 |
| 재생성할 임시 출력을 outputs에 두기 | 이 예제의 제외 정책에 맞음 |
| 과거 비밀 파일을 ignore로 숨기기 | 이미 남은 이력은 사라지지 않음 |

실제 비밀값은 실습에 쓰지 않는다. 이미 공유한 자격 증명이 노출됐다면 폐기·교체와 담당자 전달이 필요하다. 상태·커밋 검토와 제외 규칙 확인은 [통합 실습 3](../practice.md)에 모았다.

## 질문·오해

- **git add .를 쓰면 안 되나요?** 편리한 명령이지만 현재 경로 아래 원치 않는 변경도 함께 선택할 수 있다. 이번에는 대상 파일을 명시해 선택 근거를 익힌다.
- **커밋을 많이 만들수록 잘한 건가요?** 목적과 검증 근거가 읽히는지가 중요하다. 커밋 수를 성과로 쓰지 않는다.
- **잘못된 메시지는 결과도 틀렸다는 뜻인가요?** 메시지 품질과 내용 정확성은 별도다. 둘 다 확인한다.
- **폴더가 clean이면 분석 결과도 맞나요?** Git 상태만 일치한다는 뜻이다. 계산 검증을 대신하지 못한다.
- **줄바꿈 경고가 나오면 실패인가요?** 경고 원문과 설정·편집기 줄바꿈을 확인한다. 실제 의미 변경과 구분해서 판단한다.

## 핵심 요점·다음·출처

커밋은 한 목적의 변경과 검증 근거로 설명한다. ignore는 이미 추적한 파일과 과거 이력을 지우지 않는다. 다음 [04 · 복구](04-recovery.md)에서는 변경 위치와 보존 여부에 따라 행동을 고른다.
