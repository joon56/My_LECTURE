## 개념: 구현의 단위를 작게 잡고 오류를 관찰 가능한 형태로 만든다

처음부터 CSV 읽기·그래프·화면·저장까지 모두 만들면 평균이 틀렸을 때 원인 후보가 많아진다. 먼저 값 목록을 V로 바꾸고 평균을 구하는 함수를 만든다. 그 기능을 검증한 뒤 파일 읽기와 오류 처리를 붙이면 어떤 변경에서 문제가 생겼는지 찾기 쉽다. 이것은 모든 프로그램을 아주 작은 파일로 나누라는 뜻이 아니다. 한 번의 변경에서 확인할 책임을 좁히는 방법이다.

디버깅은 생각나는 수정을 계속 적용하는 일이 아니다. **재현**은 같은 입력·명령에서 같은 차이를 관찰하는 것, **가설**은 그 차이를 설명할 원인 후보, **검사**는 후보를 구별하는 행동이다. 예를 들어 평균이 20 V라면 “100으로 나눴다”와 “입력이 열 배 크다”는 서로 다른 가설이다. 입력 목록과 변환 직후 값을 보면 어느 쪽인지 좁힐 수 있다.

검사는 기대 결과가 있을 때 강해진다. `1000 mV → 1 V`는 단위 정의에서 나온다. 프로그램의 출력에 맞춰 기대값을 10 V로 바꾸면 검사가 오류를 받아들이게 된다. 먼저 계산식과 단위를 확인하고, 구현과 독립된 예상값을 둔다. 또 정상 입력 하나가 맞아도 모든 입력을 확인한 것은 아니다. 범위에 포함한 빈 목록·누락값 등은 별도 사례가 필요하다.

**최소 수정**은 증거가 가리키는 원인을 바꾸는 것이다. 단위 상수가 잘못됐는데 전체 구조를 다시 만들면 검증해야 할 범위가 늘어난다. 수정 뒤에는 실패했던 입력을 다시 실행하고 가까운 다른 사례도 확인한다. 기존 동작이 유지되는지 보는 검사를 회귀 검사라고 부른다. 필요한 검사가 통과하면 새로운 이유 없이 같은 검사를 반복하기보다 결과와 남은 범위를 기록한다.

## 강사 진행 대본

### 장면 1 — 실행 전에 정답을 적는다

**판서:** `1000, 2000, 3000 mV → 1, 2, 3 V → 평균 2 V`.

> “코드를 아직 실행하지 않겠습니다. 먼저 단위 정의로 정답을 적습니다. 이제 프로그램이 다른 값을 내면 어느 기준에 어긋났는지 설명할 수 있습니다.”

**예상 질문:** “정답을 적어두면 AI가 그것만 하드코딩하지 않나요?”

**답변:** “그래서 입력값과 변환 규칙을 함께 주고 다른 입력도 검사합니다. 500 mV 한 행에서 0.5 V가 나오는지 보면 기본 예시만 외운 구현 일부를 걸러낼 수 있습니다.”

### 장면 2 — 오류 없는 종료도 오답일 수 있다

**행동:** 아래 의도적 결함 코드를 저장하고 실행한다. 실제 화면을 보며 기록한다.

> “예상은 2인데 출력은 20입니다. 오류 메시지가 없다는 이유로 성공 처리하지 않겠습니다. 입력이 틀렸는지, 변환이 틀렸는지, 평균이 틀렸는지 나누어 보겠습니다.”

**판서:** `원본 입력 → 변환 직후 값 → 합계 / 개수`.

**예상 질문:** “그냥 AI에게 고쳐달라고 하면 안 되나요?”

**답변:** “맡길 수 있습니다. 다만 입력·예상·실제·명령을 같이 주면 원인을 확인할 수 있습니다. 수정 후에도 여러분의 기준으로 다시 검사합니다.”

### 장면 3 — 원인과 수정 범위를 연결한다

> “변환 직후가 10·20·30입니다. 평균 계산 전에 이미 열 배 커졌습니다. 변환식을 보면 100으로 나눴습니다. 1000 mV가 1 V이므로 이 상수를 1000으로 고치겠습니다.”

**행동:** `/100` 한 곳만 `/1000`으로 바꾼다. 학생에게 함수 이름 변경이나 새 라이브러리 설치가 이 오류 해결에 필요한지 설명하게 한다.

### 장면 4 — 통과한 검사와 남은 기능을 나눈다

> “기본 입력, 한 행, 0이 포함된 입력, 빈 목록을 확인합니다. 통과하면 단위 변환·평균 함수 범위에서 확인한 겁니다. CSV 파일 읽기나 그래프는 아직 검사하지 않았습니다. 완료 보고에도 그 범위를 적겠습니다.”

**예상 질문:** “테스트가 다 통과하면 버그가 없나요?”

**답변:** “정한 사례에서 기대 동작을 확인했다는 뜻입니다. 요구사항에 빠진 조건이나 검사하지 않은 경로까지 증명하지는 않습니다.”

## 완성 디버깅 예제

### 1. 의도적으로 잘못 만든 코드

아래 내용을 연습 폴더의 `mean_voltage.py`에 저장한다. 학생이 이미 만든 코드의 오류라는 설정을 붙이지 않는다.

```python
def mean_voltage_v(values_mv):
    if not values_mv:
        raise ValueError("at least one voltage is required")
    values_v = [value / 100 for value in values_mv]  # 수업용 결함
    return sum(values_v) / len(values_v)


if __name__ == "__main__":
    print(mean_voltage_v([1000, 2000, 3000]))
```

준비한 Python 환경에서 실행한다.

```powershell
python mean_voltage.py
```

**예상되는 결함 출력:** `20.0`. 정답은 `2.0`. 이는 코드로부터 도출한 기대 동작이며 학생 환경에서 실행했다고 미리 기록하지 않는다. Python 명령이 없거나 파일 경로가 틀리면 계산 오류와 분리해 환경 문제부터 해결한다.

### 2. AI에 제공할 재현 정보

```text
수업용 mean_voltage.py의 단위 변환 결함을 진단해줘.
입력: [1000, 2000, 3000] mV
실행 명령: python mean_voltage.py
예상: 2.0 V. 근거: (1+2+3)/3.
실제: 실행 화면의 값을 여기에 붙여넣는다.
변환 직후 값과 평균 계산을 구분해 원인을 확인해줘.
필요한 최소 수정만 적용하고 같은 입력과 한 행 입력으로 검사해줘.
실행하지 못한 검사는 통과했다고 적지 마.
```

`실제` 항목은 학생의 관찰로 채운다. 강사가 결과를 대신 꾸며 넣지 않는다. AI가 원인을 제시하면 코드의 상수와 단위 정의를 직접 대조한다.

### 3. 수정된 완성 함수

```python
def mean_voltage_v(values_mv):
    if not values_mv:
        raise ValueError("at least one voltage is required")
    values_v = [value / 1000 for value in values_mv]
    return sum(values_v) / len(values_v)


if __name__ == "__main__":
    print(mean_voltage_v([1000, 2000, 3000]))
```

**변경 이유:** mV를 V로 바꾸는 비율은 1/1000이다. 평균식은 이미 합계를 개수로 나누고 있으므로 이번 결함을 고치기 위해 바꾸지 않는다. 이 함수는 유한한 숫자 목록을 받는 계산 부분이다. CSV 열·문자열·결측 검증은 바깥 단계의 책임으로 두며 전체 CSV 명세를 구현 완료했다고 말하지 않는다.

### 4. 독립된 예상값으로 확인하기

같은 폴더에 `check_mean.py`를 저장한다. 일반 실행으로 확인하고 `-O` 옵션은 사용하지 않는다. Python의 최적화 실행은 `assert`를 생략할 수 있으므로 학습용 검사 목적과 맞지 않는다.

```python
from math import isclose
from mean_voltage import mean_voltage_v

cases = [
    ([1000, 2000, 3000], 2.0),
    ([500], 0.5),
    ([0, 2000], 1.0),
]

for values_mv, expected in cases:
    actual = mean_voltage_v(values_mv)
    assert isclose(actual, expected, rel_tol=0.0, abs_tol=1e-12), (
        values_mv, expected, actual
    )

try:
    mean_voltage_v([])
except ValueError as error:
    assert str(error) == "at least one voltage is required"
else:
    raise AssertionError("empty input must raise ValueError")

print("4 checks passed")
```

```powershell
python check_mean.py
```

**수정 후 기대 출력:** `4 checks passed`. 결함 코드에서는 첫 정상 사례에서 `AssertionError`가 나야 한다. 검사 코드는 실제 수정 전 실패와 수정 후 통과를 직접 관찰하도록 제공한다. 작은 오차 허용은 소수 계산 표현을 고려한 것이며, 열 배 차이는 허용 범위를 훨씬 벗어난다.

## 학생 실습: 원인 근거를 포함한 수정 보고

1. 예상값 세 개를 손으로 계산한다. 기본 2 V, 한 행 0.5 V, 0·2000 mV 평균 1 V다.
2. 의도적 결함 버전을 저장한다. 실행 명령과 실제 출력, 검사 실패를 기록한다.
3. 원인 후보 두 개를 적는다. 입력값 오류와 변환 비율 오류를 구분할 검사를 정한다.
4. 변환 직후 값을 확인하거나 해당 식을 직접 계산해 원인을 좁힌다.
5. 한 곳을 수정하고 실패했던 입력을 다시 실행한다. 검사 네 개 결과를 보존한다.
6. 공통 [실습안](../practice.md)의 CSV 명세와 비교해 아직 구현하지 않은 입력 검증·파일 읽기 항목을 적는다.

**제출 풀이 예:** “기본 입력에서 예상 2 V, 실제 20 V였다. 입력은 명세와 같았고 `/100` 변환 결과가 10·20·30 V였다. 나누는 수를 1000으로 수정했다. 수정 전 검사는 실패했고 수정 후 네 검사는 통과했다.” 마지막 두 문장은 학생이 실제 관찰했을 때만 사용한다.

**평가 10점:** 재현 입력·명령 2점, 독립 예상값 2점, 가설을 구별한 근거 2점, 최소 수정과 재검사 2점, 범위·미검증 사항 2점. 최종 코드만 제출하면 결과는 볼 수 있어도 문제 해결 과정은 확인할 수 없으므로 기록을 보완한다.

## 오개념과 완료 기준

- **“AI가 테스트를 만들었으니 독립 검증인가요?”** 같은 잘못된 가정을 검사에도 복사할 수 있다. 예상값은 단위 정의와 손계산으로 확인한다.
- **“오류 메시지가 없으면 성공 아닌가요?”** 실행 성공과 요구사항 충족은 다르다. 이번 결함도 정상 종료할 수 있다.
- **“새 기능을 많이 붙이면 완성도가 높아지나요?”** 이번 기준을 만족하는지 먼저 확인한다. 추가 기능은 새 명세와 검사가 필요하다.

실패를 재현하고 원인에 맞는 수정·재검사를 설명하면 완료다. 다음에는 Markdown을 읽고 고치는 기초를 거쳐 프로젝트 지침·기록에 이 검증 절차를 남긴다. 학생은 “코드 생성됨”, “실행됨”, “이 사례에서 검증됨”을 계속 구분한다.
