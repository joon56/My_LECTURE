# 챕터 1 실습 · 함께 만드는 블로그 회사

챕터 1 강의를 마친 뒤 강사와 같은 프롬프트를 한 번 입력해 글 한 편을 만든다. **각 담당이 자기 지침 파일을 읽고, 총괄이 실제 결과를 다음 담당에게 넘기는 과정**을 관찰한다.

주제: **AI가 만든 코드는 실행만 되면 믿어도 될까?**

## 준비 · 공통 자료와 역할 지침

사용 가능한 Codex 또는 Claude Code, 텍스트 편집기를 준비한다. 실제 하위 에이전트 지원 여부는 강사가 미리 확인한다. 두 도구를 모두 설치하지 않는다.

1. 강의 저장소 밖에 새 **blog-company** 폴더를 만든다. 같은 이름이 이미 있으면 새 이름을 쓴다.
2. [BRIEF.md](materials/blog/BRIEF.md)를 blog-company에 복사한다. blog-company 안에 agents 폴더를 만들고 [researcher.md](materials/blog/agents/researcher.md)·[writer.md](materials/blog/agents/writer.md)·[reviewer.md](materials/blog/agents/reviewer.md)를 넣는다. GitHub 저장소 전체를 내려받았다면 이 파일들은 lectures/01-ai-use/materials/blog/에 있다. 강사가 준 학생 ZIP에서는 BRIEF.md와 agents 폴더를 통째로 복사하면 된다.
3. AI의 작업 위치를 blog-company로 연다. [공통 프롬프트](instructor-prompts.md)를 읽고 코드 블록의 요청문 한 개를 입력한다. 수업에서는 강사와 함께 진행한다. 강사가 준 학생 ZIP의 PROMPT.md에도 같은 요청문이 있다. 저장소 전체 ZIP에서는 lectures/01-ai-use/instructor-prompts.md를 사용한다.

직접 파일을 저장할 때는 UTF-8 텍스트로 저장하고 .md.txt가 되지 않게 한다. README·PROMPT는 사람이 읽는 안내다. AI가 읽을 준비 파일은 아래 네 개다.

```text
blog-company/
├── BRIEF.md               공통 의뢰서: 주제·독자·반례·출처
└── agents/
    ├── researcher.md      조사 담당: 주장과 근거 정리
    ├── writer.md          집필 담당: 조사 결과로 글 작성
    └── reviewer.md        검토 담당: 초고를 자료와 대조
```

지침 파일은 각 담당의 **읽을 입력·할 일·반환 형식**을 담는다. 총괄이 파일 경로를 지정해 읽게 한다. Markdown 파일을 만든 것만으로 에이전트가 자동 등록되거나 실행되는 것은 아니다.

## 회사가 일하는 흐름

총괄은 공통 프롬프트를 받고 BRIEF.md를 읽는다. 각 담당에게 자기 지침과 BRIEF의 경로를 전달한다. 아래 화살표는 예정된 실행 순서이며 실제 수행은 도구 기록에서 확인한다.

```text
총괄이 지침 경로 전달             담당이 읽고 작업        총괄에게 반환
agents/researcher.md + BRIEF  →  조사 담당             → 주장·근거·한계
                                                            ↓ 총괄이 전달
agents/writer.md     + BRIEF  →  집필 담당 + 조사 결과  → 초고
                                                            ↓ 총괄이 전달
agents/reviewer.md   + BRIEF  →  검토 담당 + 실제 초고  → 검토 의견
                                                            ↓
필요한 수정만 같은 집필 담당에게 전달 → 총괄 확인 → article.md·work.md
```

하위 에이전트는 **3개**, 총괄까지 합하면 **4개**다. 지침과 BRIEF는 파일로 읽고, 앞 담당의 결과는 총괄이 메시지로 전달한다. 중간 결과 파일이나 단계별 폴더는 만들지 않는다. 초고가 있어야 검토할 수 있으므로 순서대로 진행한다.

## 같이 실행하기

1. 강사가 폴더에서 researcher.md를 연다. “조사 담당이 무엇을 읽고, 무엇을 돌려줘야 하는가”를 짚고 공통 프롬프트를 함께 입력한다.
2. 실제 하위 작업 화면에서 지침·BRIEF 읽기와 반환을 본다. 총괄이 조사 결과를 집필 담당에게, 초고를 검토 담당에게 넘기는 장면을 연결한다.
3. 검토 의견이 있으면 같은 집필 담당의 보완을 본다. 필수 수정이 없으면 그 판단을 확인한다.
4. article.md와 work.md를 열어 아래 항목을 함께 확인하고 끝낸다.

**예상 결과:** 준비한 네 파일은 그대로 있고 blog-company 바로 아래에 article.md(최종 글), work.md(읽은 지침·전달·수정 요약)가 생긴다. 새로운 역할이나 단계 폴더는 생기지 않는다.

## 함께 확인하고 끝내기

- 실제 하위 작업 3개와 각 역할 지침을 읽은 도구 기록이 보이는가? 응답에 “읽었다”라고 쓴 사실만으로 파일 읽기 검증이 끝난 것은 아니다. 기록이 안 보이면 미확인으로 남긴다.
- 조사 결과→초고→검토 의견이 실제로 전달됐는가? work.md에서 해당 지침 경로와 반환을 연결할 수 있는가?
- 최종 글에서 1000 mV = 1 V라는 반례를 맞게 설명했는가? 실제 수정 또는 수정 불필요 판단은 무엇인가?

별도 채점표·점수·비교 보고서는 없다. 역할 이름을 출력한 문장과 실제 작업을 구분하고, 생성된 글을 직접 읽는 수준으로 마무리한다.

## 강사용 풀이 · 파일과 행동을 연결하기

“여기 researcher.md에는 근거와 한계를 돌려달라고 적혀 있습니다. 조사 담당이 이 파일을 읽었고, 이 응답이 writer.md를 읽은 집필 담당에게 전달됐습니다.”라고 지침→실제 읽기→반환을 가리킨다. 검토도 같은 방식으로 연결한다.

이 구조에서는 공통 주제는 BRIEF, 담당별 일하는 방식은 해당 역할 파일, 실행 순서는 프롬프트에서 찾는다. 지침을 분리한 이유는 사람이 역할과 변경 위치를 쉽게 보기 위해서다. 파일을 나눴다는 사실만으로 토큰 절약·정확성 향상을 보장하지 않는다.

코드 예제의 /100은 10을 내지만 단위 정의상 1 V가 맞다. 사람이 이 차이를 대조한다. 따로 코딩·실험 단계를 추가하지 않는다.

## 막히면

파일을 못 읽으면 작업 위치와 BRIEF.md·agents/ 경로를 확인한다. 읽지 못한 담당은 멈추고 부족한 입력을 알린다. 파일 저장이 안 되면 사람이 응답을 저장하고 그 사실을 남긴다.

실제 하위 에이전트 미지원 학생은 강사 화면을 관찰한다. 강사도 미지원이면 실제 위임은 미확인이다. 실패·사용량 초과 시 멈춘 위치를 확인하고 복잡한 복구 실습으로 늘리지 않는다. [강사 환경 안내](materials/blog/TOOLS.md)를 참고한다.

실습은 제공한 역할 파일을 읽어 로컬 블로그 **원고**를 완성하는 데서 끝난다. HTML 제작·온라인 게시·Git push·호스트별 에이전트 설치는 수행 단계에 포함하지 않는다. 실제 랩실 과제는 강사가 별도로 진행한다.
