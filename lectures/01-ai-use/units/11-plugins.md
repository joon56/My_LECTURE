## 개념 설명 · 기능을 함께 배포하는 묶음

Plugin은 여러 기능을 설치·배포하기 위한 패키지다. Skill만 포함할 수도 있고 MCP 서버, hook, 보조 스크립트 등을 포함할 수도 있다. 모든 Plugin이 같은 구성 요소를 갖는 것은 아니다. manifest는 이름·버전·구성 정보 등을 호스트에 알려주는 파일이다. 지원 형식과 설치 방식은 제품마다 다르다.

Hook은 특정 이벤트가 발생할 때 설정된 동작을 실행하는 기능이다. 예를 들어 파일 편집 뒤 검사 명령을 실행하도록 구성할 수 있다. “작업 후 검사하라”는 지침과 “정해진 이벤트에 명령을 실행한다”는 설정은 다르다. Hook이 있다고 검사 자체가 올바르거나 모든 실패를 잡는 것도 아니다.

## 장면 1 · 게임 모드 상자 열기

**강사 대본**

“게임 모드를 설치하면 기능이 늘어나는 것처럼 Plugin도 작업 환경을 확장합니다. 그런데 상자 안에 무엇이 들어 있는지 봐야 합니다. 문서 검토 절차만 있는지, 외부 서비스 연결이 있는지, 파일 편집 때마다 실행되는 코드가 있는지에 따라 영향이 다릅니다. 이름과 소개 문장만 보고 판단하지 않습니다.”

**판서**

| 구성 요소 | 묻는 질문 | 예 |
|---|---|---|
| Skill | 어떤 상황에서 어떤 절차를 읽나 | CSV 검토 |
| MCP 서버 | 어떤 외부 기능·자료가 생기나 | 공식 문서 검색 |
| Hook | 언제 무엇을 자동 실행하나 | 편집 후 형식 검사 |
| 스크립트 | 실제로 읽고 쓰는 것은 무엇인가 | 결과 파일 검사 |
| Manifest | 호스트가 패키지를 어떻게 식별하나 | 이름·버전·구성 |

**학생 질문**: “Plugin은 더 강한 모델인가요?”

**예상 답**: 이 맥락에서는 작업 기능과 절차의 묶음이다. 모델 가중치를 직접 바꾸는 것으로 설명하지 않는다. 새 기능이 있어도 모델이 언제 어떻게 쓰는지와 결과 정확성은 따로 확인한다.

## 장면 2 · 가상의 패키지를 실제 질문으로 해부하기

**강사 대본**

“아래는 구조를 읽기 위한 가상 패키지입니다. 실제 제품에 설치할 수 있는 완성 manifest가 아닙니다. 네 파일의 역할부터 설명해봅시다. 내용만 읽었을 때 모르는 부분은 ‘없다’고 쓰지 않고 ‘미확인’이라고 씁니다.”

**개념용 폴더 예 — 실제 설치 규격 아님**

```text
lab-review-package/
├── package-description.md     구성과 지원 환경 설명
├── skills/
│   └── csv-review/SKILL.md    CSV 검토 절차
├── scripts/
│   └── check_result.py       결과 형식 검사 코드
└── connection-example.txt   문서 서버 연결 설명
```

**개념용 구성 설명 — 호스트가 읽는 manifest가 아님**

```text
이름: lab-review
목적: CSV 검토 보고의 누락 항목 줄이기
포함: csv-review 절차, 결과 형식 검사 코드
선택 연결: 공개 공식 문서 조회
쓰기: 지정한 results/ 검토 보고
자동 실행: 없음으로 설계; 실제 패키지 내용 대조 필요
미포함: 데이터 자동 보정, 장비 제어, 웹 게시
```

이 설명을 근거로 단정하기 전에 코드·설정과 맞는지 확인한다. 예를 들어 `check_result.py`가 결과를 읽기만 하는지 새 파일을 쓰는지는 코드 또는 실제 검사로 판단한다. “검사”라는 이름만으로 읽기 전용이라고 결론내리지 않는다.

**학생 질문**: “설명서에 안전하다고 쓰여 있으면 충분한가요?”

**예상 답**: 설명은 검토의 시작점이다. 실제 기능·접근 범위·실행 조건·호스트 권한과 맞는지 확인한다. 필요한 범위 이상으로 설정 파일이나 인증 정보를 수집할 이유는 없다.

## 장면 3 · Codex와 Claude Code의 이름이 같아도 규격 대조

**강사 대본**

“둘 다 Plugin이라는 말을 쓰더라도 폴더를 그대로 옮겨 설치할 수 있다고 가정하면 안 됩니다. 지원하는 구성 요소와 manifest, 실행 위치를 공식 문서에서 확인합니다. 우리가 지금 배우는 것은 특정 설치 메뉴를 외우는 일보다 패키지의 역할을 읽는 방법입니다.”

**공식 문서 확인, 로컬 실행 미검증 — 2026-10-03**

OpenAI 공식 Plugin 구조는 Skill, MCP 서버, 선택적 UI와 lifecycle hook 등을 설명한다. ChatGPT와 Codex의 지원 표면에 따라 일부 기능의 실행 조건이 다를 수 있다. 웹에 설치했다고 실행 환경의 hook 스크립트가 자동 배포되는 것으로 해석하지 않는다. [OpenAI Plugin architecture](https://developers.openai.com/plugins/concepts/plugins).

Claude Code는 `.claude-plugin/plugin.json` manifest와 Skill·agent·hook·MCP 같은 구성 요소를 문서화한다. `/plugin`에서 설치·활성 상태를 확인하는 경로를 제공한다. 실제 기능별 구조·지원 버전은 [Claude Code plugins](https://code.claude.com/docs/en/plugins)에서 확인한다.

수업에서는 위 경로·개념을 비교하고, 실제 도입이 필요할 때 선택한 제품의 공식 설치 절차를 따른다. 지원 여부를 확인하지 않은 범용 `plugin.json`을 만들어 두 도구에서 작동한다고 주장하지 않는다. 앞 단원의 Skill 단독 사용이나 MCP 단독 연결로 충분하면 Plugin 제작을 추가하지 않아도 된다.

**학생 질문**: “하나의 Skill도 Plugin으로 묶나요?”

**예상 답**: 지원 제품에서는 가능하다. 하지만 한 프로젝트에서만 쓰는 작은 절차를 배포 패키지로 만드는 이득이 있는지 먼저 판단한다. 여러 사람·프로젝트에 같은 구성을 배포할 때 필요가 커질 수 있다.

## 장면 4 · 도입 전후를 같은 과제로 비교하기

**강사 대본**

“설치 성공은 과제 성공과 다릅니다. 우리가 줄이려던 문제는 CSV 검토에서 누락값 위치를 빼먹는 일이었습니다. 같은 입력과 기준으로 기능 사용 전후를 비교합니다. 시간이 줄었는지, 보고 누락이 줄었는지, 불필요한 작업이 늘었는지 봅니다. 새 기능을 많이 썼다는 사실은 성과 지표가 아닙니다.”

**도입 검토 입력**

```text
현재 작업: 로컬 CSV의 입력 오류 검토
반복 문제: 누락값 위치를 보고서에서 자주 빠뜨림
기존 수단: csv-review Skill 초안
후보 Plugin 설명: CSV 검토 + 외부 저장소 동기화 + 자동 웹 게시
```

**예시 판단 결과**

```text
필요: CSV 검사·보고 절차
현재 필요 없음: 동기화·웹 게시
결정 제안: Skill 단독으로 먼저 검사
이유: 현재 문제와 직접 연결되고 확인할 구성 요소가 적음
재검토 조건: 여러 팀원이 같은 검증 도구를 반복 배포해야 할 때
```

이것은 “Plugin은 나쁘다”는 결론이 아니다. 과제의 필요와 패키지의 제공 범위를 대조한 판단이다. 이미 승인·사용 중인 기능이 있다면 기존 권한과 조건을 확인하며 작업한다. 매번 새로운 승인 절차를 만들지는 않는다.

**학생 질문**: “설치를 안 하면 실습을 못 한 건가요?”

**예상 답**: 이 단원의 기본 목표는 구성을 읽고 필요를 판단하는 것이다. 설치를 선택했다면 설치·활성·실제 호출을 별도 검사한다. 보류도 근거가 정확하면 유효한 결과다.

## 학생 실습·예시 답안·채점

공식 Plugin 소개 하나 또는 위 가상 패키지를 읽고 다음 항목을 작성한다.

```markdown
# Plugin 읽기 기록

- 해결할 반복 문제:
- 포함된 Skill·MCP·hook·코드:
- 읽는 위치와 쓰는 위치:
- 외부 연결·계정 필요 여부:
- 자동 실행 조건:
- 지원 호스트·버전 근거:
- 비활성화·해제 확인 방법:
- 도입 전후 비교 기준:
- 확인하지 못한 내용:
- 도입 또는 보류 이유:
```

예시 답안: CSV 검토 절차는 필요하지만 자동 게시의 필요는 없다. 실제 패키지에 게시를 끄는 기능이 있는지는 미확인이다. 현재는 Skill 단독 검증을 먼저 하고 패키지 도입은 보류한다. 소개에 없는 권한·해제 기능을 추측해 채우지 않는다.

채점은 구성 요소 구별, 확인/미확인 분리, 과제 필요와 도입 판단의 연결, 실제 효과 검사 계획을 본다. 설치 여부 자체는 가산점이 아니다.

## 오해·완료 확인·다음 단원

- Plugin은 Markdown 파일 모음이다 → 실행 코드·설정·연결을 포함할 수 있다.
- 같은 이름의 기능은 제품 간 호환된다 → 실제 규격·지원 범위를 대조한다.
- 설치된 기능은 매번 사용해야 한다 → 현재 과제에 필요한 것만 사용한다.

읽기 기록과 도입 판단을 설명하면 완료다. 다음은 [평가와 최종 제출](12-evaluation.md). 요청·도구·결과를 같은 기준으로 평가한다.
