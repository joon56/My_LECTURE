# 단원 12 · 같은 기준으로 비교하고 이해한 결과 제출하기

## 학습 목표·준비·산출물

- 목표: 정확성·형식·효율·이해를 나눠 평가하고 작은 비교 실험의 관찰 범위를 정확히 보고한다.
- 준비: 공통 CSV 명세, 정상·오류 입력, 비교할 요청문, 실행 기록 양식.
- 산출물: 조건별 원출력, 독립 기준으로 채점한 평가표, 최종 과제와 설명 자료.
- 완료 기준: 좋은 한 번을 일반적인 성공 보장으로 확대하지 않고, 실패와 미검증을 포함해 결과를 설명한다.

> [!NOTE]
> **PDF 연결 | 교정 후 활용**
> 물리적 35–37쪽의 여러 평가 기준·반복 실행·표현 변화·사용 모델 검증을 장면 1–3의 평가 설계로 옮긴다. 27–30쪽 사례는 “시연과 통제 실험의 차이”를 설명하는 도입 사례로 쓴다. 42–44쪽 결론은 장면 4의 인간 판단·한계 설명으로 연결한다. 원문의 일관성 지표에는 같은 클래스 정보가 필요함을 교정하고, 형식 개선을 정확성 보장으로 해석하지 않는다. 수업 채점표는 새 교육 설계다.

## 개념 설명 · 좋아 보임을 확인 가능한 기준으로 바꾸기

평가는 목적에 맞는 기준으로 결과를 대조하는 일이다. 사실이 맞는지, 요청한 형식인지, 시간과 재작업이 얼마나 드는지, 학생이 결과를 설명할 수 있는지는 서로 다른 질문이다. 표가 보기 좋아도 계산이 틀릴 수 있고, 계산이 맞아도 원본을 훼손하면 과제의 제약을 어긴 것이다.

안정성과 정확성도 다르다. 세 번 모두 평균을 2.5V라고 답하면 안정적으로 틀린 것이다. “같은 말을 한다”는 사실만으로 신뢰성을 판정하지 않는다. 원문의 Errica 외 연구는 분류 문제의 특정 지표를 다룬다. 민감성은 정답 라벨 없이 볼 수 있지만 제시된 일관성 정의는 같은 클래스 표본을 구성할 정보가 필요하다. 이 수식을 모든 자유 생성 과제에 그대로 가져오지 않는다. [원문 교정 근거](../../../research/report-review.md).

## 장면 1 · 보기 좋은 답을 먼저 의심하기보다 기준으로 읽기

**강사 대본**

“보고서의 좋은 출력 예시는 구조와 독자 적합성이 개선된 점을 보여줍니다. 그런데 그 안의 번역 성능 수치는 원논문과 대조할 필요가 있습니다. 표가 잘 정리됐다는 평가와 수치가 정확하다는 평가는 다릅니다. 오늘은 마음에 드는 답을 고른 다음 이유를 만드는 대신, 결과를 보기 전에 평가 기준을 적겠습니다.”

**판서·시연**

원본 PDF 물리적 29쪽과 *Attention Is All You Need* 초록을 나란히 연다. 기존 검토에서 그림의 영→불 BLEU 41.0 표기를 확인했고 원논문 초록은 41.8이다. 강사는 실제 그림과 원문을 학생에게 보여주며 구조 평가와 수치 평가를 나눈다. 원출력 로그가 없으므로 당시 모델·조건을 재현했다고 말하지 않는다.

**학생 질문**: “수치 하나 틀리면 프롬프트 전체가 나쁜가요?”

**예상 답**: 어떤 항목이 개선됐고 무엇이 남았는지 나눠 기록한다. 다만 중요한 사실 오류를 좋은 형식 점수로 덮어 통과시키면 안 된다. 과제에서 필수 통과 기준을 먼저 정한다.

## 장면 2 · 작은 정답 집합과 실패 사례 만들기

**강사 대본**

“정답은 모델에게 다시 물어서만 만들지 않습니다. 손으로 확인할 수 있는 작은 입력부터 시작합니다. 정상값 세 개의 평균, 누락값 한 개, 중복 시간 한 개처럼 실패 원인이 분명한 샘플을 준비합니다. 프로그램을 구현하기 전에 기대 결과를 적어야 출력에 맞춰 기준을 바꾸는 일을 줄일 수 있습니다.”

**공통 정상 입력**

```csv
time_ms,voltage_mv
0,1000
1000,2000
2000,3000
```

**독립된 기대값**

```text
time_s: 0, 1, 2
voltage_v: 1, 2, 3
mean_voltage_v: (1 + 2 + 3) / 3 = 2
전압 그래프 축: V, 시간 축: s
```

**작은 평가 집합**

| 사례 | 바꿀 입력 | 기대 결과 |
|---|---|---|
| N 정상 | 위 세 행 | 변환값·평균 2V 일치 |
| M 누락값 | 데이터 2행 전압을 비움 | 위치 보고, 정상 요약 중단 |
| T 비숫자 | 전압에 `error` | 열·위치·이유 보고 |
| D 중복 시간 | 마지막 시간을 1000으로 변경 | 중복 시간 보고 |
| R 역순 | 시간 0, 2000, 1000 | 역순 정책에 따라 오류 보고 |

각 사례는 원본을 보존하고 새 결과를 구별해 확인한다. 이전 정상 실행의 `summary.json`이 남아 있을 수 있으므로 파일 존재만으로 이번 오류 입력에서 요약이 생성됐다고 판단하지 않는다. 실행별 결과 폴더를 분리하거나 변경 시점·출력 내용을 확인한다.

**학생 질문**: “이 다섯 사례를 통과하면 완벽한가요?”

**예상 답**: 해당 사례를 통과한 것이다. 큰 파일, 인코딩, 실제 장비 데이터, 다른 환경 등 아직 다루지 않은 조건은 남는다. 범위를 적고 중요한 실패를 발견하면 사례를 추가한다.

## 장면 3 · 요청문 비교의 조건을 통제하기

**강사 대본**

“A에는 짧은 요청, B에는 조건과 기준을 줍니다. B가 더 좋은 결과를 내더라도 어떤 문장 하나 때문인지 바로 알 수는 없습니다. 역할·길이·예시를 동시에 바꾸면 여러 요인이 함께 바뀐 겁니다. 수업에서는 효과를 관찰하되 작은 시연의 결과를 모든 모델의 성능 향상률처럼 발표하지 않습니다.”

**비교 입력**

```text
A: 첨부한 측정 CSV를 분석해줘.

B: 첨부한 측정 CSV의 time_ms, voltage_mv를 검증하고 s, V로
변환해줘. 누락값·비숫자·중복·역순 시간은 위치와 이유를 보고하고
정상 요약을 만들지 마. 정상 입력은 평균과 그래프를 별도 저장해줘.
원본은 보존해줘. 실제 실행과 기대값 비교, 미검증을 보고해줘.
```

비교 목적은 “요구사항을 명시한 요청이 이 과제에서 어떤 차이를 보이는가”다. 특정 단어의 인과 효과를 분리하는 실험은 아니다. 각 조건은 같은 자료·도구 접근·프로젝트 지침으로 새 대화에서 시작한다. 모델 표시명, 날짜, 메모리·검색 사용 여부를 기록하고 알 수 없는 설정은 미확인으로 둔다. 조건 순서를 바꾸고 같은 횟수로 실행한다. 조건당 3회 같은 수업 규모는 관찰용이며 일반적인 우월성 추정에는 작다.

**실행 기록 양식 — 결과는 실행 후 채움**

```text
조건/회차:
입력 사례·파일 식별:
모델 표시명·도구·날짜:
프로젝트 지침·메모리·검색 조건:
원출력 위치:
실제 실행한 명령·결과:
기대값과 차이:
요청 충족/오류 정책/원본 보존:
시간·추가 질문·재작업:
판정과 미확인:
```

**가상 평가 예 — 실제 모델 성능 결과 아님**

| 조건 | 정상 3회 | 누락값 3회 | 해석 |
|---|---|---|---|
| A | 평균 모두 맞음 | 1회 자동 삭제 | 누락값 정책 문제 관찰 |
| B | 평균 모두 맞음 | 모두 중단·위치 보고 | 이 작은 표본에서 정책 준수 |

“B가 안전성을 100% 보장한다”는 결론은 낼 수 없다. “제시한 가상 관찰에서는 B의 누락값 처리 오류가 관찰되지 않았다”가 가능한 범위다. 실제 수업에서는 성공만 남기지 말고 실패·중단·도구 미사용도 기록한다.

**학생 질문**: “A가 더 잘 나오면 실습이 실패한 건가요?”

**예상 답**: 관찰을 바꾸지 않는다. 실제 조건과 출력으로 왜 그랬는지 조사한다. 원하는 결론이 나올 때까지 반복한 뒤 그 결과만 제출하면 비교가 왜곡된다.

## 장면 4 · 최종 제출에서 사람의 판단 드러내기

**강사 대본**

“최종 제출은 코드와 예쁜 그래프만 모으는 일이 아닙니다. 무슨 문제를 풀었고, 무엇을 맡겼고, 어떤 기준으로 맞다고 판단했는지 보여줘야 합니다. AI가 많이 했다는 사실을 숨길 필요도, 사람이 하지 않은 일을 했다고 쓸 이유도 없습니다. 본인이 한 선택 세 개와 아직 모르는 것 하나를 설명해봅시다.”

**최종 제출 구조 예**

```text
submission/
├── README.md              목표·실행법·핵심 결과
├── requirements.md        입력·출력·제약·완료 기준
├── src/                   실행 코드
├── samples/               정상·오류 입력
├── results/               결과·그래프
├── evaluation.md          예상값·실행·실패·한계
├── instructions-example.md  수정한 지침과 이유
└── handoff.md             현재 상태·다음 행동
```

평가표는 교육 제안이다. 기능 설치 수에 점수를 주지 않는다.

| 평가 영역 | 배점 | 확인할 내용 |
|---|---:|---|
| 문제 정의 | 20 | 단위·입출력·오류 정책·완료 기준 |
| 구현과 결과 | 20 | 명세에 맞는 동작·원본 보존 |
| 검증 | 30 | 독립 기대값·오류 사례·실행 증거·한계 |
| 기록과 인계 | 15 | 작성/검증/확인 상태·다음 행동 |
| 직접 설명 | 15 | 자신의 판단과 코드·자료 연결 |

필수 통과 항목은 점수와 별도로 둔다. 원본 보존, 단위·평균 정확성, 오류 입력의 명세 준수, 실행 여부의 정직한 기록을 충족해야 한다. 총점이 높아도 해당 항목 실패는 보완한다.

**학생 질문**: “코드를 다 외워야 설명한 건가요?”

**예상 답**: 입력이 어디서 들어오고 어떻게 검증·변환되어 출력되는지, 핵심 정책을 왜 택했는지, 어떤 증거로 확인했는지 설명하면 된다. 모르는 부분은 위치를 찾아 확인하는 방법까지 보여준다.

## 학생 실습·예시 답안·오해

“좋은 프롬프트로 세 번 성공했으므로 이제 오류가 없다”는 결론을 고친다. 위 평가 집합에서 빠진 조건 두 개와 확인 방법을 제안한다.

예시 답안: “정상 샘플의 세 실행에서 평균 2V를 확인했다. 오류 입력과 실제 장비 데이터는 아직 검증하지 않았다. 다음은 누락값·비숫자 사례를 실행하고 오류 위치와 정상 출력 중단을 확인한다.” 동일 성공 횟수만으로 전체 신뢰도·인과관계를 확정하지 않는다.

추가 실습으로 [의견 조건 비교](../practice.md)의 N·W·C·G를 사용한다. 같은 자료에서 사용자 의견만 바꾸고 정답 2V와 대조한다. 맞는 주장에 동의하는 것은 오류가 아니며, 모든 조건이 맞으면 해당 과제에서 동조 오류가 관찰되지 않았다고 쓴다.

## 완료 확인·다음 시작점

학생은 명세, 코드·결과, 예상값과 실행 기록, 수정한 지침, 인계 자료를 제출한다. 짝이 실행법을 읽고 재실행하며 작성자는 핵심 판단 세 가지와 한계를 설명한다. 재실행하지 못한 경우 원인을 기록하고 인계 성공으로 처리하지 않는다.

다음은 [챕터 2 기획](../../02-git-and-records/plan.md). 이번 결과·판단·검증 기록을 Git의 변경 이력, GitHub 협업, 블로그·포트폴리오 설명으로 연결한다. 현재 폴더 공개·배포는 별도 작업이다.
