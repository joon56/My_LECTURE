# 챕터 1 실습 · 블로그 제작사 운영하기

챕터 1 강의를 모두 들은 뒤 진행한다. 여러분은 작은 블로그 제작사의 편집장이다. AI에게 맡길 일과 사람이 확인할 일을 나누고, 요청이 결과에 미친 차이를 관찰한다.

**공통 주제: 「AI가 만든 코드는 실행만 되면 믿어도 될까?」**

주제와 독자는 모두 같다. 학생이 직접 정할 것은 **업무의 경계, 요청 문장, 근거를 확인하는 방법, 결과를 받아들이거나 고칠 기준**이다. 먼저 자기 프롬프트 A로 수행하고 저장한다. 그 뒤 강사의 masterpiece prompt B를 공개해 같은 입력에서 다시 수행한다. B는 설계 의도를 읽어볼 교육용 기준본이며, 항상 더 좋은 결과를 보장하는 정답은 아니다.

## 0. 준비 · 빈 폴더부터 시작

### 준비물과 자료의 의미

- 파일 편집기, 웹 브라우저, 사용할 수 있는 Codex 또는 Claude Code 하나. 도구·계정·모델은 A/B에서 유지한다.
- [BRIEF.md](materials/blog/BRIEF.md): 발주 조건, 모든 학생에게 공개된 완료 기준과 비교 조건.
- [SOURCES.md](materials/blog/SOURCES.md): S1~S3 공식 문서의 URL·확인 위치·교재 요약. 원문 전문은 아니다.
- [CASES.md](materials/blog/CASES.md): C1 단위 변환, C2 근거표, C3 결함 원고, C4 고정 원고, C5 변경 요청, C6 인계 상태.
- [TOOLS.md](materials/blog/TOOLS.md): 하위 에이전트 지원 확인과 실제 호출 관찰 방법. 공식 문서 확인과 학생 환경 실행 확인을 구분한다.

강의 저장소를 편집하지 않는다. 바탕 화면 등 강의 저장소 밖에 **새 `blog-lab` 폴더**를 만든다. 이미 같은 이름이 있으면 `blog-lab-2`처럼 새 이름을 쓴다. 강사 프롬프트 파일이나 강의 전체를 학생 작업 폴더로 복사하지 않는다.

1. 위 세 입력 자료 링크를 열고 각각의 **Markdown 원문 전체**를 복사한다. `blog-lab/inputs` 폴더를 만들고 `BRIEF.md`, `SOURCES.md`, `CASES.md`로 UTF-8 저장한다. 다운로드했다면 파일을 이 폴더에 복사한다.
2. 실제 확장자가 `.md.txt`가 아닌지 확인한다. `BRIEF.md`의 공통 제목, `SOURCES.md`의 S1~S3, `CASES.md`의 C1~C6이 보이면 준비 자료 복사 완료다. 렌더링된 표만 복사해 원문이 빠졌다면 다시 원문을 저장한다.
3. `blog-lab`에서 터미널을 연다. PowerShell 사용자는 아래 명령으로 비교 폴더와 입력 사본을 만든다. 다른 환경은 파일 탐색기로 같은 구조를 만든다. 명령은 **처음 준비할 때 한 번** 수행한다.

```powershell
1..7 | ForEach-Object {
    $stage = 'S{0:D2}' -f $_
    foreach ($condition in @('A', 'B')) {
        $trial = Join-Path $stage $condition
        New-Item -ItemType Directory -Path (Join-Path $trial 'out') -Force
        New-Item -ItemType Directory -Path (Join-Path 'notes' $trial) -Force
        Copy-Item -LiteralPath 'inputs/BRIEF.md', 'inputs/SOURCES.md', 'inputs/CASES.md' -Destination $trial
    }
}
New-Item -ItemType Directory -Path 'final' -Force
```

예상 구조: `S01`부터 `S07`까지 각 A/B에 같은 입력 세 파일과 빈 `out` 폴더가 생긴다. `notes`는 학생의 비교 기록, `final`은 마지막 연속 제작 공간이다.

```text
blog-lab/
├── inputs/                 원본 사본 3개, 수정하지 않음
├── S01/A/                  BRIEF.md, SOURCES.md, CASES.md, out/
├── S01/B/                  A와 같은 입력, 빈 out/
├── S02/ … S07/             각각 A와 B
├── notes/S01/A/            prompt.md, response.md, run.md
├── notes/S01/B/            B 실행 후 같은 기록
├── notes/S01/compare.md    A/B 판정과 자기 개선문 C
├── notes/ …                S02~S07도 같은 방식
└── final/                  비교 후 자기 방식으로 글 한 편 제작
```

AI에는 **지금 실행할 `S01/A`처럼 가장 안쪽 폴더만 작업 폴더로 연다.** `blog-lab` 전체를 열면 형제 폴더의 B 결과·기록이 섞일 수 있다. 각 실험에서 부모·형제 폴더를 읽지 않도록 같은 경계를 적용한다. A/B의 공통 초기 지침·메모리·도구 접근 조건을 확인하고 `notes/environment.md`에 적는다. 달랐거나 확인할 수 없으면 비교 한계로 남긴다.

### 공통 발주 조건

독자는 AI로 프로그램 과제를 해본 공대 1~2학년이다. 한국어 본문은 공백 포함 1,200~1,800자를 목표로 한다. 제목·코드·참고문헌은 글자 수에서 제외한다. 소제목 3~5개, 단위 변환 반례 하나, 독자가 해볼 확인 세 가지, 주장에 연결된 출처, 검증의 한계를 담는다. 실제로 하지 않은 실행·학생 성과·향상률을 만들지 않는다. S04의 짧은 교정문, S05의 고정 짧은 원고, S06의 변경 분량은 해당 단계 조건을 따른다.

기본 비교에서는 제공 자료만 쓴다. 온라인 원문 대조는 최초 A/B 비교를 기록한 뒤 별도 검증으로 수행하고, 비교 당시 읽은 자료와 나중에 확인한 원문을 구분한다. 도구 설치나 새 블로그 플랫폼 가입은 기본 과제가 아니다. 강의 속 CSV는 검증 원리를 설명하는 별도 예제다. 기존 CSV 자료를 수정하거나 이번 실습의 입력으로 준비할 필요는 없다.

## 1. 매 상황의 공통 순서 · A → B → 자기 개선문 C

S01~S07은 **각각 독립 비교**다. S03은 S02에서 잘 나온 결과를 이어받지 않고 C2로 다시 시작한다. 앞 단계의 성공·실패가 다음 단계 비교를 바꾸지 않게 하기 위해서다. 실제 제작처럼 결과를 이어 쓰는 활동은 마지막 `final`에서 한다.

1. **A 설계:** 해당 상황의 입력·산출물·평가 기준을 읽는다. 자신이 선택할 사항을 먼저 메모하고 프롬프트를 직접 쓴다. 교사의 문장을 먼저 보지 않는다.
2. **A 실행:** 해당 A 폴더에서 새 세션으로 시작한다. 요청·원응답·실제 생성물을 보존한다. 프롬프트는 `notes/Sxx/A/prompt.md`, 원응답은 `response.md`, 환경·실제 호출·시간·표시 사용량·수정 횟수는 `run.md`에 저장한다. 표시되지 않은 토큰은 `미확인`으로 쓴다.
3. **A 판정:** 입력과 결과를 직접 대조하고 공개 기준으로 점수를 쓴다. 마음에 들지 않는 출력도 지우지 않는다. 수정했다면 최초 출력과 수정 이유를 모두 남긴다.
4. **B 공개·실행:** A 기록을 저장한 뒤에만 [강사용 masterpiece prompts와 풀이](instructor-prompts.md)의 해당 상황을 연다. B 폴더의 새 세션에서 B만 실행한다. A 프롬프트·결과·대화는 보내지 않는다. 기록 위치만 `notes/Sxx/B`로 바꾼다.
5. **비교:** `notes/Sxx/compare.md`에 요구별 차이, 확인한 근거, 호출·수정 부담, 아직 모르는 점을 적는다. 같은 조건의 A가 더 좋거나 차이가 없어도 그대로 쓴다.
6. **C 작성:** 자기 A의 어느 구절을 왜 바꿀지 쓴다. B 전체를 복사하는 대신 필요한 설계를 자기 문장에 반영한다. 재실행이 필요하면 새 C 폴더에 원본 입력을 복사하고 별도 기록한다. C를 최초 A/B 결과와 섞지 않는다.

호출 예산은 **A/B 각각 최초 요청 1회와 보완 요청 최대 1회**다. S02는 총괄 하나와 하위 두 개 이내, 각 하위 조사 1회이며 재귀 생성하지 않는다. 나머지는 단일 에이전트다. 기본 온라인 검색은 0회다. 강사가 실행 전에 같은 시간 상한을 정하고 학생은 이를 기록한다. B만 추가 호출·자료·시간을 주면 동등 비교가 아니다. 초과했으면 초과 사실과 추가 결과를 분리해 적는다. 한 번씩의 결과 차이로 프롬프트의 인과효과나 일반적 우월성을 확정하지 않는다.

### 공통 평가 · 단계마다 A/B 각각 8점

| 축 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 요구 충족 | 핵심 결과 없음·다른 과제 | 결과 있으나 공개 조건 누락 | 해당 단계 조건·산출물 충족 |
| 근거 | 꾸며낸 사실·검증 | 출처 있으나 주장 연결·한계 부족 | 입력과 주장 연결, 실제/미확인 구분 |
| 위임 통제 | 작업 범위·권한 이탈 | 경계 있으나 중복·누락 발생 | 필요한 범위·인원·도구를 통제 |
| 재작업 | 결함·다음 행동 설명 불가 | 결함은 찾았으나 수정 범위 불명확 | 보존/수정/재실행 범위와 이유 명확 |

단일 에이전트 단계에서도 위임 통제를 평가한다. 불필요한 작업을 늘리지 않고 필요한 일만 맡겼는지가 기준이다. C 작성 전 발견·기록한 수정 판단까지 평가하되 C의 개선 결과를 A/B 점수에 소급하지 않는다. 점수마다 실제 파일의 문장이나 호출 기록 하나를 근거로 붙인다. 보기 좋은 문체만으로 사실 오류를 상쇄하지 않는다.

## S01. 발주를 작업 계획으로 바꾸기

**목표·이유:** 정해진 글을 만들기 위해 무엇을 먼저 해야 하는지 정한다. 좋은 문장을 요청하기 전에 입력·완료 기준·선행 작업을 맞춘다.

**입력:** `BRIEF.md`. 주제를 새로 정하지 않는다. 자료 조사와 원고 작성은 아직 수행하지 않는다.

**학생이 결정할 것:** 업무를 몇 묶음으로 나눌지, 각 묶음의 입력과 결과, 순차·병렬 순서, 사람이 승인·검증할 지점. 모든 직함마다 에이전트를 만들 필요는 없다.

**프롬프트 미션:** 독자·목적·성공 기준을 확인하고 실행 가능한 계획을 요청한다. 업무마다 입력→할 일→산출물→완료 기준을 연결하는 방식을 스스로 정한다. 누가 어떤 파일을 만들지와 선행 결과가 필요한 지점을 전달한다.

**예상 산출물:** `out/plan.md`. 독자, 요구 목록, 업무 분해, 의존 관계, 위임할 일과 총괄이 맡을 일, 판단 이유가 있어야 한다.

**직접 평가:** 계획만 따라도 마지막 글의 조건을 검사할 수 있는가? 근거가 준비되기 전에 사실 원고부터 확정하지 않는가? 병렬 조사와 순차 검토가 구분되는가?

**A/B 비교 질문:** 내 요청에서 빠진 조건을 AI가 임의로 결정했는가? B의 어떤 문장이 그 결정을 명시하게 했는가? 업무가 많아진 것이 실제로 필요한가?

**막히면:** 역할 이름만 나열되면 업무 하나를 골라 입력·출력·완료 기준부터 보완한다. 계획 대신 글이 나왔으면 원출력을 남기고 이번 요청의 종료 지점을 고친다.

## S02. 실제 하위 에이전트에 조사 위임하기

**목표·이유:** 서로 독립된 조사를 나누고 총괄이 검증·통합한다. 한 답변에 여러 직함을 붙이는 역할극과 별도 맥락에서 수행한 하위 작업을 구분한다.

**입력:** `BRIEF.md`, `SOURCES.md`, `CASES.md`의 C1. 조사 범위는 두 묶음이다. ① S1+C1: 실행과 정확성, 코드 검토. ② S2+S3: `assert`와 평가의 조건·한계.

**학생이 결정할 것:** 각 범위의 담당, 넘길 맥락, 주장·근거·한계의 반환 형식, 총괄의 대조 방법. 두 묶음은 병렬 가능하다. 총괄 포함 최대 세 에이전트이며 하위 작업의 재귀 생성은 금지한다. 역할당 조사 응답은 핵심 12줄 안팎으로 제한한다. 학생 A도 이 인원·자료 조건을 미리 안다.

**프롬프트 미션:** 도구가 지원하는 실제 하위 에이전트 두 개를 명시적으로 요청한다. 각 하위 작업의 목적·읽을 자료·결과 형식·읽기 전용 범위·중단 조건을 자기 문장으로 전달한다. 결과는 총괄이 받아 자료와 대조한 뒤 파일로 통합하게 한다.

**실행 절차:**

1. [도구 안내](materials/blog/TOOLS.md)로 현재 환경의 지원을 확인한다. 전역 설정을 임의로 바꾸지 않는다. A/B 모두 같은 실행 방식으로 진행한다.
2. A 요청을 실행한 뒤 실제 하위 작업 생성 표시·작업 식별자·도구 호출 기록을 확인한다. 하위 두 개가 각각 받은 입력과 반환한 응답을 보존한다.
3. 총괄의 결과와 각 하위 결과를 대조한다. C1의 예상값 `1000 mV = 1 V`를 사람이 계산하고 `/100`이면 `10 V`가 되는 반례를 확인한다. 계산 확인과 Python 실행은 별개다.
4. 기록에 실제 호출·완료/실패·미확인을 적는다. 총괄의 “위임했다”는 문장만으로 생성 성공을 인정하지 않는다. 이어 공통 순서대로 B와 비교한다.

**미지원 대체:** 새 대화 두 개를 직접 열어 같은 두 범위만 전달하고 응답을 총괄 대화로 수동 전달한다. A/B 모두 이 방식을 쓴다. `수동 시뮬레이션 — 실제 하위 에이전트 기능 미검증`으로 표시한다. 별도 대화도 불가능하면 위임문·검증 계획까지 제출하고 실제 실행은 미완료로 남긴다.

**예상 산출물:** `out/evidence.md`에 주장·출처 ID·확인 위치·적용 한계·독립 계산을 정리한다. `out/delegation.md`에는 하위 작업별 범위, 실제 식별자/호출 증거, 반환 결과, 총괄 대조, 미확인 사항을 남긴다.

**직접 평가:** 실제 두 하위 작업의 증거가 있는가? 중복 조사·입력 원본 수정·추가 에이전트가 없는가? 통합 과정에서 `assert`의 조건이나 평가 한계를 지우지 않았는가?

**A/B 비교 질문:** 어떤 인계 정보가 빠져 재질문했는가? 서로 다른 범위를 맡겼는데 같은 요약만 받았는가? 추가 호출에 비해 얻은 근거가 무엇인가?

**막히면:** 지원되지 않는 기능은 성공으로 꾸미지 않는다. 한 하위 작업이 실패하면 실패 범위와 총괄이 대신 확인한 범위를 나눠 기록한다. AI가 만든 가짜 작업 ID는 실제 호스트 기록과 대조한다.

## S03. 근거표로 원고 작성하기

**목표·이유:** 자료를 그럴듯한 주장으로 부풀리지 않고 독자에게 설명한다. 조사 결과의 양보다 주장과 근거의 연결을 본다.

**입력:** `BRIEF.md`, `SOURCES.md`, `CASES.md`의 **C2 고정 근거표**. S02에서 실제 생성한 `evidence.md`는 가져오지 않는다. A/B 모두 E1~E5에서 시작한다.

**학생이 결정할 것:** 독자의 오해를 풀 설명 순서, 반례의 배치, 각 출처를 붙일 주장, 확인 방법과 한계를 드러내는 문장. 교육용 제안과 공식 문서의 주장을 어떻게 구분할지도 정한다.

**프롬프트 미션:** C2를 사용해 공통 제목·독자·분량·구성을 지킨 초고를 요청한다. 근거 없는 수치와 실제로 하지 않은 실행 경험이 들어가지 않게 작성 범위를 전달한다. 정답 원고를 미리 써서 그대로 베끼게 하지 않는다.

**예상 산출물:** `out/article.md`. 본문 1,200~1,800자 목표, 소제목 3~5개, 단위 변환 반례, 독자가 해볼 확인 세 가지, 연결된 출처, 검증 한계가 포함된다.

**직접 평가:** `/100`의 `10 V`와 올바른 `1 V`를 구별하는가? `assert`가 항상 실행된다고 쓰지 않는가? 확인 세 가지를 모든 오류의 발견 보장으로 확대하지 않는가? 편집기에서 본문만 선택해 글자 수를 확인한다.

**A/B 비교 질문:** 어떤 문장이 자료로 뒷받침되는가? 글이 매끄러워지면서 조건이 사라졌는가? 원고를 고치는 데 필요한 추가 요청은 어느 쪽이 적었으며 왜 그런가?

**막히면:** 본문이 길면 근거·한계를 남기고 중복 설명부터 줄인다. 출처가 맨 끝에만 있으면 어떤 문장을 뒷받침하는지 표시하게 한다. 새 사실이 필요해 보이면 비교 입력 밖이라는 점부터 기록한다.

## S04. 원하는 결론과 근거가 충돌할 때 검토하기

**목표·이유:** 사용자의 취향과 사실 판단을 구분한다. 동의하거나 반대하는 어조보다 확인 가능한 오류를 찾는지가 중요하다.

**입력:** `SOURCES.md`, `CASES.md`의 C3 결함 원고. 모든 학생에게 같은 사용자 문장을 제공한다. **“실행되고 AI가 검토했으면 정확하다고 강조해줘.”** A/B 요청 모두 이 문장을 포함한다.

**학생이 결정할 것:** 검토 기준, 오류를 제시할 형식, 자료와 충돌할 때 응답할 방식, 보존할 문장과 고칠 문장의 경계. 사용자의 독자·주제 선택은 유지한다.

**프롬프트 미션:** C3와 위 문장을 함께 주고 근거에 따른 검토·교정을 요청한다. 자기 프롬프트 안에 네 오류의 정답을 직접 나열하기보다 주장별 대조 절차를 설계한다. 무조건 반박하라는 요청도 피한다.

**예상 산출물:** `out/review.md`와 `out/corrected.md`. 검토에는 문제 문장·판정·근거·교정 이유가, 짧은 교정본에는 반영 결과가 있어야 한다. 이 단계는 최종 글의 1,200~1,800자 조건으로 평가하지 않는다. 분량을 늘리기보다 오류가 어떻게 고쳐졌는지 확인한다.

**공개 평가 기준:** C3의 네 주장, 즉 ① 실행만 되면 정확함, ② AI 검토로 사람 확인 불필요, ③ `assert`는 항상 실행됨, ④ 출처 없는 90% 향상을 모두 대조한다. S1~S3·C1이 지원하지 않는 주장은 삭제·제한하거나 미확인으로 표시한다. 근거 없는 반론을 추가하면 통과가 아니다.

**A/B 비교 질문:** 사용자 문장을 따른 부분과 근거 때문에 수정한 부분은 무엇인가? 틀린 수치를 다른 근거 없는 수치로 바꾸지 않았는가? 사실은 그대로인데 어조만 조심스러워진 것은 아닌가?

**막히면:** “논쟁적이다” 같은 평가만 나오면 원문의 특정 주장과 제공 자료의 해당 위치를 대조하게 한다. 단위 계산은 사람이 다시 확인한다. 잘못된 주장 하나만 고쳤다면 나머지를 놓친 이유를 기록한다.

## S05. 원고를 읽을 수 있는 페이지로 만들기

**목표·이유:** 파일 생성과 화면 검증을 구분한다. 글의 근거를 보존하면서 사람이 읽고 링크를 열 수 있는 결과로 바꾼다.

**입력:** `CASES.md`의 **C4 고정 짧은 원고**, `BRIEF.md`, 출처 확인용 `SOURCES.md`. S03·S04 결과는 가져오지 않는다. C4를 1,200~1,800자로 새로 늘리지 않는다.

**학생이 결정할 것:** 읽는 순서, 글의 너비와 글자 크기, 예제·확인 목록·출처의 표현, 좁은 화면에서 확인할 기준. 디자인 취향과 필수 기능을 구분한다.

**프롬프트 미션:** C4의 제목·본문·코드 예제·출처를 보존하는 HTML 한 파일을 요청한다. CSS는 파일 내부에 둔다. 외부 이미지·폰트·패키지·서버 없이 열 수 있어야 한다. 도구가 파일만 만들 수 있는지 브라우저도 확인할 수 있는지 구분하게 한다. 단일 에이전트로 진행한다.

**예상 산출물:** `out/post.html`과 `out/preview-check.md`. HTML 파일 존재만으로 미리보기 검증 완료라고 쓰지 않는다.

**사람이 직접 확인하는 절차:**

1. 파일 탐색기에서 해당 `S05/A/out/post.html`을 브라우저로 연다. 확장자가 `.html.txt`이면 바로잡는다.
2. 제목·본문·반례·확인 세 가지·출처가 C4와 일치하는지 대조한다. 오류 예제의 `/100`과 교정 설명의 `1000`이 표시 과정에서 달라지지 않았는지 본다.
3. 보통 창 너비와 좁힌 창에서 글·코드·링크가 겹치거나 잘리는지 확인한다. 가능하면 개발자 도구에서 390px 너비도 본다. 실제로 본 너비·브라우저를 기록한다.
4. 출처 링크를 눌러 목적지를 확인한다. 인터넷이 없으면 주소만 대조하고 링크 접속은 미검증으로 남긴다. 가로 스크롤이 생기는지 확인한다.
5. `preview-check.md`에 검사 항목·예상·관찰·판정·못 한 검사를 적는다. B도 같은 화면 조건에서 확인한다.

**직접 평가:** 원문과 근거가 보존됐는가? 외부 자산 없이 표시되는가? 읽을 수 있고 출처로 이동 가능한가? 실제 화면을 보지 않은 항목은 미검증인가?

**A/B 비교 질문:** 요구한 디자인이 읽기에 어떤 영향을 주었는가? B의 지시가 실제 결함을 줄였는가? 생성 성공 보고와 사람의 관찰이 일치하는가?

**막히면:** 브라우저에 코드 텍스트만 보이면 확장자와 저장 내용을 확인한다. 원고가 바뀌면 문장 차이부터 고친다. 서버 설치를 제안받으면 HTML 한 파일 조건을 다시 전달하고 추가 제안은 기록만 남긴다.

## S06. 독자 변경에 필요한 일만 다시 하기

**목표·이유:** 조건 하나가 바뀌었을 때 재사용할 근거와 다시 쓸 설명을 구분한다. 모든 단계를 재실행하는 비용을 피하면서 변경 조건은 지킨다.

**입력:** `CASES.md`의 C4 원고와 C5 변경 요청, `SOURCES.md`. 독자를 **코딩 경험이 없는 신입생**으로 바꾸고 본문을 **700~1,000자**로 맞춘다. 주제·근거·반례·확인 세 가지·한계는 유지하며 추가 검색은 하지 않는다.

**학생이 결정할 것:** 바꿀 용어와 설명 깊이, 그대로 쓸 근거, 다시 확인할 요구, 재실행하지 않을 일과 이유. 앞 단계의 디자인·조사를 자동으로 다시 시킬 필요는 없다.

**프롬프트 미션:** 먼저 변경 영향을 분류하고 필요한 원고 부분만 수정하게 한다. 새 독자를 위해 어떤 설명을 보충·축약할지 자기 기준을 전달한다. 원고와 설명을 바꾸는 데 별도 조사·번역·하위 에이전트가 필요한지 판단한다.

**예상 산출물:** `out/revision-plan.md`에 재사용/수정/재검사 대상과 이유, `out/revised.md`에 변경된 글. HTML 재제작은 이번 비교의 산출물이 아니다.

**직접 평가:** 비전공 독자가 용어와 반례를 이해할 수 있는가? 본문 분량을 확인했는가? 쉬워진 설명에서 사실·출처·한계가 사라지지 않았는가? 추가 조사·새 역할을 만들지 않았는가?

**A/B 비교 질문:** 무엇을 다시 하지 않아도 된다고 판단했는가? 단순 축약과 독자 맞춤 설명의 차이가 나타나는가? 생략 때문에 검증에 필요한 정보가 빠졌는가?

**막히면:** 전문용어를 삭제했지만 문장이 모호하면 짧은 설명을 붙인다. 분량이 넘으면 새 주장보다 중복을 줄인다. 원고 전체를 다시 써도 근거까지 다시 조사해야 하는 것은 아니다.

## S07. 내 작업 규칙과 다음 세션의 인계 만들기

**목표·이유:** 한 번의 요청, 반복할 규칙, 현재 상태를 분리한다. 다음 사람이 이전 대화 없이 무엇을 확인해야 하는지 알게 한다.

**입력:** `BRIEF.md`와 `CASES.md`의 **C6 가상 인계 상태**. 원고와 HTML 파일은 작성 완료로 보고됐고, 브라우저 표시 미확인, 외부 게시 안 함이다. 실제 원고·HTML 파일은 이 단계에 제공되지 않는다. 작성 보고와 파일 존재·내용 확인을 구분한다. 이 단계는 C6의 상태를 정리하는 연습이며 학생 본인의 S05 실행 결과와 섞지 않는다.

**학생이 결정할 것:** 매번 필요한 운영 규칙, 이번 작업 상태에만 속하는 내용, 다음 행동 하나, 새 세션에 넘길 최소 자료. AI 보고와 사람이 확인한 사실을 구별한다.

**프롬프트 미션:** 선택한 도구의 프로젝트 지침 초안, 사실에 맞는 상태 기록, 재개 요청문을 작성하게 한다. 과거 대화 전문보다 필요한 파일·상태·미검증·다음 행동을 전달한다. 없는 사용자 승인이나 실행 기록을 만들지 않게 한다.

**예상 산출물:** Codex는 `out/AGENTS.md`, Claude Code는 `out/CLAUDE.md`. 공통으로 `out/STATUS.md`, `out/handoff.md`. 지침 파일에 반복 규칙, STATUS에 현재 상태, handoff에 읽을 자료와 다음 행동을 둔다. 파일명은 `AGENT.md`가 아니라 `AGENTS.md`다.

**직접 평가:** C6를 가상 상태라고 밝혔는가? 작성 완료 보고·파일 확인 전·표시 미검증·미게시가 구분됐는가? 사용자 무응답을 합의로 바꾸지 않았는가? 다음 행동이 실제 파일 확인 뒤 브라우저 검사로 이어지는가? Markdown 코드 블록·상대 링크·파일명을 확인한다.

**A/B 비교 질문:** 다음 사람이 무엇을 먼저 읽게 되는가? 기록만 보고 실행 완료를 과장할 위험이 있는가? 반복 규칙에 일회성 상태가 들어가 낡을 가능성은 없는가?

**막히면:** “전체 완료”를 항목별 상태로 바꾼다. 지침 초안이 만들어졌다고 자동 적용을 주장하지 않는다. 이 단계의 파일은 `out` 안 초안이며 실제 호스트 로딩·행동 검사는 별도다. 적용 방식은 [도구 안내](materials/blog/TOOLS.md)를 확인한다.

## 2. 최종 제작 · 자기 프롬프트로 블로그 한 편 완성

여기부터는 독립 A/B 비교가 끝났다. 좋은 결과만 골라 붙이는 대신 **자기 프롬프트와 실제 단계별 결과를 이어서** 제작한다. S06의 독자 변경은 비교 연습이므로 최종 글은 원래 BRIEF의 공대 1~2학년·1,200~1,800자 조건으로 돌아온다.

1. `inputs`의 세 파일을 `final`로 복사하고 `final/out`, `final/notes`를 만든다. 기존 비교 결과는 보존한다. AI 작업 폴더를 `final`로 열고 새 세션에서 시작한다.
2. 각 단계에서 배운 내용을 반영한 **자기 최종 프롬프트**를 `final/notes/prompts.md`에 쓴다. 채택·수정·제외한 문장과 이유를 짧게 남긴다. 강사 기준본을 그대로 복사한 것을 자작으로 표시하지 않는다.
3. 자기 계획→실제 조사→초고→근거 검토→수정 원고→HTML 순서로 이어간다. 집필 입력은 고정 C2 대신 실제 조사 근거표, 검토 입력은 C3 대신 자신의 초고, HTML 입력은 C4 대신 검토를 반영한 최종 원고다. 실제 조사 결과가 없으면 먼저 그 단계를 완료하며 고정 사례를 몰래 대신 쓰지 않는다. S02의 인원·호출 경계를 지키며 불필요한 재조사는 하지 않는다.
4. 검토 결과를 `final/out/review.md`에 남긴다. 사람이 원고의 주장과 S1~S3·C1을 대조한다. 단위 예상값·`assert` 조건·근거 없는 수치·분량·출처·검증 한계를 확인하고 `final/notes/checks.md`에 근거를 적는다. AI의 “문제없음”만으로 끝내지 않는다.
5. `final/out/post.html`을 직접 열고 S05의 화면·링크 검사 방법을 적용한다. 내용은 자신의 최종 원고와 대조하며 C4는 사용하지 않는다. 문제가 있으면 수정 이유와 재검사 결과를 남긴다. 못 한 검사는 계속 미검증으로 표시한다.
6. 최종 원고를 `final/out/article.md`, 출처 연결을 `final/out/sources.md`에 정리한다. `final/STATUS.md`에는 실제 생성·검증·미확인·미게시 상태와 다음 행동을 쓴다. C6의 가상 상태를 복사하지 않는다.
7. 자기 방식의 규칙이 필요하면 S07 초안을 고쳐 `final/AGENTS.md` 또는 `final/CLAUDE.md`로 둔다. 저장, 호스트에서 읽힘, 실제 행동을 각각 기록한다. 아직 확인하지 않은 자동 적용은 주장하지 않는다.

**최종 내보내기:** `final/export` 폴더를 직접 만들고 검토한 `article.md`, `post.html`, `sources.md`만 `final/out`에서 복사한다. 블로그 글 한 편의 전달 묶음이다. 비교 기록·대화·상태·개인정보가 실수로 포함되지 않았는지 파일 목록을 확인한다.

**선택 게시:** 이미 쓰는 블로그가 있다면 사람이 최종 파일을 확인하고 직접 업로드할 수 있다. 게시 전 제목·본문·출처·코드 표시와 공개 범위를 다시 확인한다. 새 플랫폼 설치·자동 업로드·외부 공개는 기본 완료 조건이 아니다. 게시하지 않았다면 `로컬 내보내기 완료, 미게시`로 기록한다. Git과 GitHub 발행은 챕터 2에서 다룬다.

### 최종 제출과 직접 설명

제출: `notes/S01~S07`의 A/B 원요청·원응답·실행 기록·비교·자기 개선문, 각 상황의 `out`, `final`의 자기 프롬프트·검사 기록·최종 파일·상태. 가짜 성공 대신 실제 실패와 다음 행동을 적어도 학습 판단의 근거가 된다.

학생은 다음 네 가지를 결과 파일을 가리키며 설명한다.

- 내가 정한 업무 경계 하나와 위임 이유. 실제 하위 에이전트인지 수동 시뮬레이션인지.
- A/B 차이 하나, 그 판단의 근거, 차이가 없거나 확정할 수 없는 부분.
- 자기 프롬프트에서 바꾼 구절 하나와 관찰한 효과 또는 아직 미검증인 이유.
- AI가 만들었어도 사람이 직접 확인한 항목 하나, 남은 한계와 다음 행동 하나.

**완료 판정:** 로컬 블로그 한 편, 출처 대조와 사람의 화면 확인, 정직한 실행 기록, 자기 선택 설명이 있어야 한다. 하위 에이전트 미지원은 실제 실행 성공과 구분해 제출한다. 확인하지 못한 항목이 있으면 결과물 생성과 검증 완료를 따로 판정한다.

## 3. 풀이 확인과 강의 개념 연결

각 상황의 A 기록을 저장한 뒤 [강사용 masterpiece prompts·설계 해설·풀이](instructor-prompts.md)에서 **해당 상황만** 확인한다. 강사는 다음 상황의 기준본을 미리 보여주지 않는다. 학생 결과가 기준본과 다르다는 이유만으로 감점하지 않고 공개 조건과 증거로 판정한다.

공통 8점 평가는 프롬프트의 길이나 역할 수를 측정하지 않는다. 예를 들어 출처 있는 보기 좋은 글도 `assert`의 조건을 지우면 근거 항목을 통과하지 못한다. 짧은 요청이 모든 조건을 충족했다면 그 성과를 인정한다. 실제 학생 수행·교육 효과는 수업 후 관찰할 대상이다.

| 강의 개념 | 연결 활동 | 학생이 남길 증거 |
|---|---|---|
| 01 모델·호스트·도구 | S02, S05 | 실제 하위 호출, 파일 생성과 화면 확인의 구별 |
| 02 오류·검증·동조 | S03, S04 | 독립 예상값, 주장·출처 대조, 사용자 문장 교정 |
| 03 작업 명세 | S01, S06 | 입력·산출물·완료 기준, 의존 관계·변경 범위 |
| 04 프롬프트 | 모든 A/B/C | 자작 요청, 관찰한 차이, 수정 구절·이유 |
| 05 맥락 | S02, S07 | 하위 작업에 넘긴 자료, 다음 세션의 최소 자료 |
| 06 작은 구현 | S05, 최종 제작 | HTML 생성→관찰→최소 수정→재검사 |
| Markdown 기초 | S03, S07 | 원문·코드 블록·링크·지침 파일 확인 |
| 07 프로젝트 지침 | S07, 최종 제작 | 반복 규칙과 현재 상태 분리, 적용 상태 기록 |
| 08 기록·인계 | S07, 최종 제작 | 생성/검증/미확인/미게시와 다음 행동 |
| 09 Skill | 선택 확장 | 반복 절차의 범위·입력·실패 처리 초안 |
| 10 MCP·11 Plugin | 도구 선택 설명 | 이번 과제에서 추가 연결·설치가 필요한지 판단 |
| 12 평가 | 모든 비교·최종 제출 | 같은 입력·예산·환경, 점수 근거, 일반화 한계 |

### 선택 확장 · 반복 절차를 Skill 초안으로

같은 검토 절차가 실제로 반복됐다면 일반 문서 `final/notes/blog-review-SKILL.md`에 적용 상황·필요 입력·검토 순서·중단 조건·결과 형식을 써본다. `name`, `description` 메타데이터와 본문 범위를 대조한다. 초안 작성은 설치·호스트 로딩·행동 검증과 별개다. 기본 수업에서는 Skill·MCP·Plugin 설치를 추가하지 않는다.
