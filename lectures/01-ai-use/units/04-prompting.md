# 4. 결과를 얻는 프롬프트와 예시 작성

[이전: 작업 명세](03-specification.md) · [전체 설계](../plan.md) · [다음: 맥락 관리](05-context.md)

## 목표·준비·제출물

학생은 같은 과제를 자유 요청, 형식 지정, 예시 제공으로 구분해 작성한다. 목표·관찰·가설을 분리하고, 출력이 빗나갔을 때 어떤 정보나 기준을 고쳐야 하는지 설명한다. 선수 지식은 단원 3의 명세와 합성 CSV 단위다. 제출물은 `04-prompts.md`: 요청문 세 버전, 평가 기준, 실제 관찰 또는 실행 전 상태다. 특정 주문을 외웠는지가 아니라 필요한 조건을 전달했는지를 평가한다.

>
> 23~26쪽의 CoT·self-consistency·Tree of Thoughts·least-to-most는 심화 선택 자료다. 역사적 기법과 적용 과제를 소개하되 모든 현대 추론 모델의 기본 주문으로 권장하지 않는다. **추가 내용:** 사용자 가설 표시와 동조 비교, 요청문 버전별 채점은 [추가 조사](../../../research/markdown-and-sycophancy.md)를 반영했다.

## 개념: 좋은 요청은 이번 행동을 판단할 조건을 준다

기본 구성은 `목적 + 현재 상태 + 근거 자료 + 제약 + 산출물 + 완료 기준`이다. 매번 여섯 제목을 쓸 필요는 없다. “이 세 전압의 평균을 V로 구해줘. 입력 단위는 mV야”처럼 짧아도 조건이 충분하면 된다. 반대로 길어도 “오류 행을 삭제하라”와 “모든 행을 보존하라”가 충돌하면 먼저 정책을 정해야 한다.

**역할**은 관점과 독자를 정하는 데 쓴다. “학부생에게 설명하는 조교처럼”은 용어 난이도와 설명 방식의 안내다. “세계 최고 전문가”라는 문구가 새로운 사실 지식이나 실행 증거를 제공하지는 않는다. **구조**는 지시와 자료를 구분한다. 코드 블록 안 CSV는 계산 대상이고 그 아래 문장은 요청이다. 자료에 적힌 문장을 모두 실행 지시로 받아들여서는 안 된다.

**형식 지정**은 결과의 모양을 정한다. `행 수 / 평균 / 오류 목록`이라는 제목만 제공하면 형식 지시다. **예시 기반 요청**은 실제 입력과 기대 출력의 짝을 제공한다. 완성된 예 한 개는 one-shot, 여러 개는 보통 few-shot이라 부른다. 예시가 틀리거나 현재 규칙과 충돌하면 오히려 오류를 유도할 수 있으므로 예시도 검증해야 한다.

추론 모델에 긴 내부 사고 전사를 기본으로 요구할 필요는 없다. 교육에서는 수식과 풀이 설명을 요청할 수 있다. 실무에서는 “가정, 계산식, 근거 위치, 검사 결과를 보여줘”처럼 사람이 확인할 항목을 지정한다. 정답이 짧게 출력됐다는 이유만으로 모델 내부 계산이 단 한 번의 토큰 예측이었다고 단정하지 않는다. CoT 관련 권고는 모델 유형과 과제 범위를 함께 읽는다.

의견도 종류를 나눠 전달한다. “그래프를 선호한다”는 목표·취향, “로그에서 값이 튄다”는 확인할 관찰, “센서 고장일 것”은 가설이다. AI가 내 뜻을 존중하면서 가설을 자료로 검증하도록 요청할 수 있다. 모든 사용자 의견에 반대하는 답은 원하는 결과가 아니다.

## 강사 진행 대본

### 장면 1 — 긴 요청보다 빠진 조건을 찾는다

**화면:** `너는 최고의 공학 전문가야. 이 데이터를 완벽하게 분석해줘.`

> “이 문장에는 좋은 결과를 원한다는 뜻은 있습니다. 하지만 단위, 필요한 출력, 삭제해도 되는 값은 없습니다. 전문가라는 단어를 더 붙이는 대신 이번 결과를 바꾸는 정보를 넣겠습니다.”

**판서:** `무엇을 / 어떤 자료로 / 어디까지 / 무엇으로 확인`.

**예상 질문:** “말을 정중하게 하면 더 잘하나요?”

**답변:** “이 수업의 평가 기준은 정중함이 아닙니다. 요구사항과 근거를 명확히 하고 결과를 확인합니다. 동조 연구를 정중한 질문 자체가 오류를 만든다는 결론으로 바꾸지 않습니다.”

### 장면 2 — 형식과 예시를 손으로 구분한다

**행동:** PDF 29쪽 요약 형식을 보여준 뒤 아래 예시 두 개와 나란히 놓는다.

> “여기는 제목을 지정했습니다. 여기는 실제 입력에서 어떤 결과가 나와야 하는지 보여줍니다. 둘 다 도움이 될 수 있지만 같은 기법은 아닙니다. 형식은 모양을, 예시는 규칙을 구체적으로 전달합니다.”

**예상 질문:** “출력 예시만 주면 few-shot인가요?”

**답변:** “출력 모양의 본보기는 될 수 있습니다. 이번 수업에서는 입력과 기대 출력 쌍을 갖춘 예시와 구분해 부르겠습니다. 평가할 변수가 선명해집니다.”

### 장면 3 — 답을 유도하는 전제를 수정한다

**화면:** `마지막 값은 오류니까 빼줘.`

> “삭제 요청 안에 ‘오류다’라는 미확인 판단이 숨어 있습니다. ‘마지막 값이 크다. 센서 오류라는 가설을 확인하고 싶다. 원본은 보존해 달라’로 바꿔 보겠습니다. 삭제 기준이 이미 합의됐다면 그 기준을 주면 됩니다.”

**판서:** `목표 / 관찰 / 가설 / 확인 요청 / 허용 행동`.

### 장면 4 — 응답을 고칠 때 결함을 특정한다

> “‘다시 잘해줘’ 대신 ‘평균 수치는 맞지만 단위가 없다. V를 표시하고 변환식을 붙여줘’라고 말합니다. 틀린 부분과 유지할 부분을 알려야 불필요하게 전체 결과가 바뀌는 일을 줄일 수 있습니다.”

**예상 질문:** “매번 단계별로 생각하라고 해야 하나요?”

**답변:** “기본 문구로 강제하지 않습니다. 여러분이 검토할 수식·근거·검사를 요청하세요. 어떤 방식이 도움이 됐는지는 실제 사용하는 모델과 과제에서 평가합니다.”

## 완성 예제: 같은 CSV를 세 방식으로 요청하기

공통 자료는 `time_ms,voltage_mv` 헤더와 `0,1000`, `1000,2000`, `2000,3000` 세 행이다. 세 요청 모두 입력 단위는 ms·mV, 평균의 대상은 전체 데이터 행으로 고정한다.

### A. 자유 요청

```text
아래 CSV의 전체 전압 평균을 V로 구해줘. voltage_mv의 단위는 mV다.
time_ms,voltage_mv
0,1000
1000,2000
2000,3000
```

### B. 형식 지정

```text
아래 CSV의 전체 전압 평균을 V로 구해줘. voltage_mv의 단위는 mV다.
출력 항목은 n, mean_voltage_v, check 순서로 작성해줘.
check에는 사용한 변환식과 평균식을 짧게 적어줘.
time_ms,voltage_mv
0,1000
1000,2000
2000,3000
```

### C. 검증한 예시 두 개 추가

```text
voltage_mv를 1000으로 나눠 V로 변환한 뒤 전체 행의 산술평균을 구해줘.
출력 항목은 n, mean_voltage_v, check다.

예시 1 입력: voltage_mv = [1000, 3000]
예시 1 출력: n=2; mean_voltage_v=2; check=(1+3)/2=2 V
예시 2 입력: voltage_mv = [500]
예시 2 출력: n=1; mean_voltage_v=0.5; check=500/1000=0.5 V

실제 입력:
time_ms,voltage_mv
0,1000
1000,2000
2000,3000
```

**기대 결과:** 세 요청 모두 평균 2 V. B·C는 `n=3`, `mean_voltage_v=2`, `(1+2+3)/3=2 V`에 해당하는 검사 근거가 있어야 한다. C에서 예시 두 개의 행 수를 실제 입력에 섞지 않는다. A에는 세 항목 출력 요구가 없으므로 그 형식을 따르지 않았다는 이유로 지시 불이행 감점을 주지 않는다.

**비교 방법:** 정확성은 같은 정답으로, 형식 준수는 각 요청의 실제 요구로 채점한다. 추가 예시가 반드시 성능을 높인다고 정해 놓지 않는다. 이 예는 단순해서 A도 충분할 수 있다. 복잡한 결측 정책을 설명할 때 예시가 더 필요할 수 있지만, 그 경우에는 먼저 처리 정책을 명세에 고정한다.

## 학생 실습: 요청문 수정과 결과 평가

**시작 문장:** `평균은 2.5 V 맞지? 전문가처럼 단계별로 생각해서 보기 좋게 정리해줘.`

1. 목적, 사실 주장, 역할, 출력 요구에 밑줄을 각각 긋는다.
2. 평균 2.5 V는 미검증 가설로 표시한다. CSV와 단위를 붙이고 계산으로 대조하도록 바꾼다.
3. `결론 / 계산 근거 / 미확인 사항`이라는 형식을 지정한다.
4. 실수하기 쉬운 입력·정답 쌍 두 개를 만든다. 예: 500 mV 한 행은 0.5 V, 0·2000 mV 두 행은 평균 1 V다.
5. 요청을 실제 실행했다면 원문 응답을 보존하고 사실 정확성·형식·가설 교정·불필요한 삭제를 따로 평가한다.
6. 응답 결함 하나에 대해 수정 요청을 쓴다. 결함이 없으면 요청을 더 길게 늘리지 말고 확인한 기준을 적는다.

**풀이 예:** “내 예상은 2.5 V이지만 확인하지 않았다. 아래 CSV로 평균을 계산하고 다르면 수정해줘. 원본을 바꾸지 말고 결론·계산 근거·미확인 사항으로 답해줘.” 정확한 응답은 2 V와 계산식을 제시한다. 가설을 검증하라는 문구를 넣었다는 사실과 실제로 오답을 교정했다는 사실은 별도로 기록한다.

**평가 10점:** 자료·단위 2점, 목표와 가설 분리 2점, 형식·예시 구분 2점, 검증된 예시 2점, 관찰에 근거한 수정 요청 2점.

## 오개념·종료 기준

- **“짧은 프롬프트는 나쁜가요?”** 충분한 정보가 있으면 짧아도 된다. 길이로 품질을 판정하지 않는다.
- **“few-shot이면 정답을 보장하나요?”** 예시 범위를 벗어난 입력과 예시 자체의 오류를 확인해야 한다.
- **“자기 일관성 다수결이 원문보다 낫나요?”** 반복 합의는 원문 수치나 실제 실행 검사를 대체하지 않는다.

학생이 A·B·C 차이를 설명하고 자기 요청의 가설과 검사 기준을 표시하면 완료다. 다음 [단원 5](05-context.md)는 긴 작업에서 필요한 자료를 고르고 최신 상태를 유지하는 방법이다.
